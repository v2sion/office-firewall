## STEP 2 — 배포 (키 필요)

Vercel 팀(`v2sioninmymind-4818s-projects`)을 만들고 `office-firewall` 프로젝트를
GitHub(`v2sion/office-firewall`, production branch `main`)에 연결해 뒀다 — 이제
`main` 에 푸시하면 자동으로 배포된다. **환경변수는 대시보드에서 직접 넣을 것**
(API 키를 채팅 세션에 노출하지 않기 위해 의도적으로 이렇게 함):

1. https://vercel.com/v2sioninmymind-4818s-projects/office-firewall/settings/environment-variables
2. **Production** 환경에 추가:
   - `GROQ_API_KEY` = (본인 키, console.groq.com 에서 발급)
   - `GROQ_MODEL` = `openai/gpt-oss-20b` (라이브 검증 완료. 이 계정에서 실제로
     응답하는 모델은 `openai/gpt-oss-20b` / `120b` 뿐이다 — STEP 3 참고)
3. 저장 후 재배포 트리거 (`main` 에 새 커밋을 푸시하거나, 대시보드에서 Redeploy)

CLI 로 처음부터 하고 싶으면 대안:

```bash
cd office-firewall
npx vercel link --project office-firewall --yes
npx vercel env add GROQ_API_KEY production
npx vercel env add GROQ_MODEL production        # 값: openai/gpt-oss-20b
npx vercel --prod
```

배포 후 확인:

- [x] 페이지가 뜨는가 — https://office-firewall.vercel.app
- [x] 분석 실행 시 모드 배지가 **AI 분석** 인가 — STEP 3 실측에서 5종 모두 `mode: live` 확인
- [ ] `vercel.json` 의 `maxDuration: 25` 가 현재 플랜에서 거부되지 않았는가
      (빌드 로그에 경고가 뜨면 15 로 낮추고, 그때는 `CALL_TIMEOUT_MS`(현재 9초)도
      함께 확인 — 타임아웃 × 재시도가 함수 제한을 넘으면 안 된다)

## STEP 3 — LIVE 실측 ✅ 완료 (2026-09-18, 커밋 `bd18cb3`)

배포본에서 골든 5종을 실제 Groq 호출로 돌려 **전부 기대 구간 통과**를 확인했다.

| 골든 시나리오 | 점수 | 등급 | 기대 구간 | 지연 | 토큰(in/out) |
|---|---|---|---|---|---|
| ① 주말 침범 | 84 | red | 61~100 | 1,250ms | 2,240 / 531 |
| ② AI 슬롭 | 48 | amber | 41~100 | 1,736ms | 2,195 / 863 |
| ③ R&R 핑퐁 | 64 | orange | 41~100 | 2,099ms | 2,185 / 654 |
| ④ 클라이언트 갑질 | 79 | orange | 61~100 | 20,073ms | 2,219 / 648 |
| ⑤ 정상 업무 대조군 | 8 | green | 0~20 | 1,288ms | 2,197 / 689 |

- 사용 모델: `openai/gpt-oss-20b` (Groq 무료 티어)
- 평균 지연: 정상 응답 기준 1.2~2.1초
- 프롬프트 캐싱: Groq 미지원이라 `cache_read_input_tokens` 는 항상 0 (정상)

**심사 기간에 주의할 것 — 처리량 상한:**
무료 티어는 **8,000 TPM** 이고 호출당 약 2,500~2,900 토큰이 나간다. 즉
**서비스 전체가 분당 약 3건**이 상한이다. ④ 의 20초는 429 직후 SDK 자동
재시도가 TPM 창을 기다린 값으로, `maxDuration` 25초에 아슬아슬했다.

- 한도를 넘으면 429 → 클라이언트가 로컬 룰엔진으로 폴백하고 배지가 `오프라인 분석`
  으로 바뀐다. 화면이 비지는 않으므로 심사 중 치명적이지는 않다.
- 심사위원이 몰릴 것 같으면 console.groq.com 에서 Dev Tier 로 올리거나,
  시연 직전에는 연속 실행을 피할 것.

> 수 있는 답장) 를 앞에 두고 차별점을 뒤에 붙였다. 200자 제한에 62자가 남는다.

**해결하고자 한 문제 (68자, 그대로 붙여넣기):**

```
주말·밤에 오는 애매한 업무 메시지. 정당한 요구인지 판단할 기준이 없어 답장을 썼다 지웠다 반복하다 결국 혼자 떠안는다.
```

> 예전 문장(61자)은 "메시지가 불명확하다"까지만 말하고 **사람이 치르는 비용**이

> 바로 이어지는 문장이라, 심사위원이 제목과 묶어 읽을 때 앞뒤가 맞는다.

**AI 활용 방식 및 결과 (457자, 그대로 붙여넣기):**

```
원칙 — 판단을 LLM에게 맡기지 않습니다.

① 선-마스킹: 이름·전화·이메일을 브라우저에서 토큰으로 바꾼 뒤 전송합니다. 무엇이 나가는지 전송 전에 전문으로 확인할 수 있고, 원본과 토큰의 대응표는 브라우저 메모리에만 남습니다.

③ 점수는 규칙 엔진: 권력 비대칭 40·긴급도 20·모호성 20·알맹이 결여 20. 배점은 근로기준법(야간근로 22~06시 등)과 고용노동부 직장 내 괴롭힘 매뉴얼에서 가져왔고, 근거 조문을 화면에서 펼쳐 볼 수 있습니다. 같은 입력이면 항상 같은 점수입니다.
④ 답장 3종 생성: 그대로 보낼 수 없는 문장은 코드가 규칙 엔진 답장으로 교체합니다. 자동 테스트 286개로 고정했습니다.
```

## 부록 A — 고용노동부 기준 코퍼스

커뮤니티 코퍼스가 "사람들이 실제로 받는 메시지"를 본다면, 이쪽은 **판단 기준 쪽**을
본다. 고용노동부 「직장 내 괴롭힘 판단 및 예방·대응 매뉴얼」의 행위 예시와 판단 유형을
메시지 한 통으로 옮겨, 인정형 5 · 불인정형 4 · 판정 불가 2로 정리했다
(`test/fixtures/moel-corpus.json`).

```bash
node scripts/live-corpus.mjs moel                       # 로컬 규칙 엔진
node scripts/live-corpus.mjs moel https://<배포주소>     # 실제 LIVE
```

> 메시지 본문은 실제 접수 사건의 문구가 아니다. 진정·신고 원문은 공개되지 않고,
> 공개된 판정문 문구를 옮기면 제3자 저작물이 된다. 매뉴얼의 **예시 항목과 판단 유형**을
> 업무 메시지 한 통으로 새로 옮긴 것이다.

**불인정형이 이 코퍼스의 핵심이다.** 우리 과잉방어 대조군은 여태 우리가 쓴 정상 메시지
두 개뿐이었다. 고용노동부가 "괴롭힘 아님"으로 본 유형에서 가져오면, 과잉방어를 막는
기준이 우리 취향이 아니라 행정 기준이 된다.

### 이 코퍼스가 잡아낸 결함 3가지

**① 긴급성을 위험으로만 봤다** — 가장 큰 건이다.

```
"밤 11시에 죄송합니다. 결제 서버 장애로 고객 결제가 전부 실패하고 있습니다."  → 52점
"밤 11시인데 미안해요. 그 자료 지금 한번 봐줄 수 있어요?"                  → 52점
```

매뉴얼과 행정해석은 근무시간 외 연락을 "업무 관련성, 필요성, **긴급성**, 빈도"로 함께
보라고 한다. 즉 긴급성은 위험을 키우는 요소가 아니라 **정당화하는 요소**다. 제56조도
야간근로를 금지하지 않고 가산수당 대상으로 정할 뿐이다. 지금은 장애·사고처럼 지금
대응하지 않으면 손해가 커지는 사유가 본문에 있으면 시간대 가산을 하지 않는다
(**20점 · 정상**). "대표님 보고가 잡혀서" 같은 내부 일정은 사유로 치지 않는다.
"장애 **없이** 잘 돌아가는지"처럼 부정형도 제외한다 — 사유 인정은 점수를 깎는
방향이라 여기서의 오탐이 곧 과소경보가 되기 때문이다.

**② "오늘 18시까지"를 당일 마감으로 못 잡았다** — `"오늘까지"`만 문자열로 찾고 있어서
시각이 붙으면 전부 통과했다.

**③ 촉박한 마감 자체에 20점을 얹고 있었다** — 매뉴얼은 "업무량이 많거나 마감이 촉박한
것 자체는, 특정인을 겨냥한 부당한 배분이라는 사정이 없는 한 괴롭힘으로 보기 어렵다"고
한다. 당일 마감은 야간·휴일과 달리 법이 시간대를 지정한 보호구간도 아니다. 모호성·알맹이
결여와 겹칠 때만 센다.

| | 점수 |
|---|---|
| "오늘 18시까지 견적서 1종만. 양식은 지난번 것 그대로" | 20 · 정상 |
| "오늘 중으로 다시 작업해서 보내주세요. 뭔가 좀 아닌 것 같아요." | 85 · 심각 |

### 못 보는 것

매뉴얼 예시 중 **감시·집단 배제**처럼 기간에 걸친 행위는 메시지 한 통으로 판정할 수
없다(`testable: false`로 남겨 뒀다). 반복 신호는 점수가 아니라 방어 기록이 맡는다.

`urgencyType`·`ambiguityType` 이 값 하나씩이라 신호가 겹쳐도 한 번만 센다. 밤에 일해서
아침까지 내놓으라는 요구는 야간 침범과 당일 마감이 겹치지만 20점만 붙는다. 겹침을
더하려면 배점 구조를 바꿔야 하는데 네 축은 조문에 대응시켜 정한 값이라 근거 없이 더할
수 없다. 그래서 **과소평가 쪽으로 틀린다** — 이 제품에서는 과잉경보보다 그쪽이 안전하다.

## 부록 B — 커뮤니티 사연 코퍼스로 돌려 본 결과

골든 5종은 우리가 설계 단계에서 고른 시나리오라, **우리가 생각한 모양의 메시지만**
들어 있다. 직장인 커뮤니티에 사연으로 올라오는 메시지는 결이 다르다 — 요구가 아예
없거나(되받기), 기한만 있고 산출물이 없거나, 업무가 아닌 지시다.

그 결을 재현한 12종 코퍼스(`test/fixtures/community-corpus.json`)로 전 구간을
돌렸다. 실제 게시물을 옮기지 않고 유형만 가져와 새로 썼다 — 원문을 넣으면 제3자
저작물이 되고, 확인하려는 것도 특정 글이 아니라 "이런 결의 메시지"이기 때문이다.

```bash
node scripts/live-corpus.mjs                       # 로컬 규칙 엔진
node scripts/live-corpus.mjs https://<배포주소>     # 실제 LIVE (/api/analyze)
OFW_SHOW_REPLIES=1 node scripts/live-corpus.mjs    # 답장 본문까지
```

> LIVE 러너는 무료 티어 처리량(8,000 TPM ≈ 분당 3건)에 맞춰 호출 사이에 21초를
> 둔다. 12건이면 약 4분이다. 429 가 나면 그 건만 '혼잡'으로 표시하고 넘어간다.

### 이 코퍼스가 잡아낸 결함 2가지

**① 기한이 있으면 "범위 불명"이 꺼졌다**

> "밤 11시에 미안한데 방금 확인해 보니까 숫자가 좀 이상한 것 같아요.
>  내일 오전에 바로 쓸 거라 지금 한 번만 봐줄 수 있을까요?"

어느 숫자가 왜 이상한지, 무엇이 맞는 상태인지가 없다. 그런데 **"내일 오전"이라는
기한이 적혀 있다는 이유로** 알맹이 게이트에 막혀 모호성 "없음"이 나왔다 — 52점(주의).
기한이 있다는 사실은 산출물이 특정됐다는 뜻이 아니다. 기준을 대지 않고 다시 하라고
요구하는 표현("~이상한 것 같", "뭔가 좀 아닌")을 게이트를 타지 않는 쪽으로 옮겼다.
지금은 72점(경계)이다.

**② 판정과 답장이 정면으로 어긋났다**

정상 업무 대조군(16점·green, 화면에는 "요구 모호성: 없음 · 범위·기한 명확"이 뜬다)에도
답장이 `"세부 조건이 명확하지 않아 진행 전 네 가지만 확정하고 싶습니다"`로 시작했다.
룰엔진이 "비어 있지 않다"고 판정한 메시지에 답장은 "비어 있다"고 말한 것이다. 둘 중
맞는 쪽이 무엇이든 **둘 다 못 믿게 된다.**

- 규칙 엔진: 모호성이 "없음"이면 없는 결함을 요구의 근거로 쓰지 않고, 내 일정·우선순위
  처럼 사실인 근거로 바꾼다.
- LIVE 지시문: 같은 규칙을 명시했다 — "네가 방금 내린 판정과 어긋나는 말을 답장에
  쓰지 마라."
- 회귀 테스트: 코퍼스 12종 × 톤 3 × 목적 4 전부에서 확인한다.

### 알아 두고 갈 한계 — 정서적 가해는 측정하지 않는다

> "다들 이 정도는 하는데 왜 유독 힘들어하는지 모르겠네요. 너무 예민하게 받아들이지
>  말고 편하게 생각해요."

39점(경미)이 나온다. **이건 결함이 아니라 설계다.** 네 축은 근로기준법 제76조의2의
①"지위·관계의 우위"와 ②"업무상 적정범위"에 대응하고, ③"신체적·정신적 고통"은
일부러 넣지 않았다(README "배점의 근거" 참고). 주관적 피해를 측정하는 척하는 순간
이 점수가 법적 판단처럼 읽히기 때문이다.

심사위원이 이런 메시지를 붙여넣고 "왜 낮게 나오죠?"라고 물으면 **그 자리에서 답할 말이
있어야 한다**:

> "위험 지수는 요구의 위험도를 재지 정서적 가해의 크기를 재지 않습니다. 고통은 저희가
> 측정할 수 있는 값이 아니고, 측정하는 척하면 이 점수가 법적 판단처럼 읽힙니다.
> 대신 이런 메시지의 값어치는 점수가 아니라 **방어 기록에 쌓였을 때의 패턴**입니다.
> 같은 상대에게 같은 신호가 반복되면 그게 '기분 탓'이 아니라는 근거가 됩니다."
