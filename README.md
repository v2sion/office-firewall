> 직장에서 받은 애매한 메시지의 **숨은 요구**와 **빠진 알맹이**를 진단하고,
> 내가 원하는 톤으로 보낼 수 있는 답장을 만들어 주는 도구.

## 무엇을 푸는가

> "시간 될 때 가볍게 한번 봐주시면 좋을 것 같아요. 급한 건 아닙니다!"

직장인이 실제로 지치는 지점은 업무량이 아니라 **이런 문장을 해석하는 비용**이다.
급한 게 아니라면서 월요일 보고가 잡혀 있고, 범위도 기한도 담당도 비어 있다.
수락하는 순간 그 빈칸을 전부 내가 메우게 된다.

Office Firewall 은 이 메시지를 넣으면 세 가지를 돌려준다.

1. **X-Ray 진단** — 표면 문장과 실제 요구의 차이, 그리고 위험 지수(0~100)
2. **대응 답장 3종** — 대응 방향(칼차단·시간벌기·공넘기기·관계보존) × 말투 세기(순한맛~매운맛)
3. **오피스 방어 영수증** — 공유 가능한 카드. 옆에는 EAP 무료 심리상담 링크

## 어떻게 다른가 — 설계 결정 3가지

이 세 가지가 "ChatGPT 에 프롬프트 한 줄" 과 이 제품을 가르는 지점이다.

**1. AI 는 추출만 하고, 점수는 규칙이 계산한다**

AI 에게 위험도를 매기게 하면 같은 메시지가 매번 다른 점수를 받는다. 그래서 AI 는
"주말 침범인가", "기한이 명시됐나" 같은 **사실 추출**만 하고, 점수는
`src/lib/score.js` 의 공식이 계산한다. 같은 입력이면 항상 같은 점수가 나오고,
**판정 근거를 화면에서 그대로 펼쳐 보여줄 수 있다.**
AI 가 지어낸 클리셰는 원문과 대조해 걸러낸다.

**2. 원문을 AI 에 보내지 않는다**

이름·연락처·금액은 **브라우저에서 먼저 가린 뒤**에야 서버로 나간다. 토큰 맵
(어떤 토큰이 누구인지)은 그 브라우저 메모리에만 있고 전송·저장되지 않는다.
그리고 **"전송될 내용 확인"** 으로 실제 전송본을 사용자가 직접 볼 수 있다 —
약속이 아니라 확인 가능한 사실로 만든 것이 요점이다.

**3. 진단을 먼저 보여주고, 답장은 그 아래에 둔다**

답장부터 주면 사용자는 상황을 이해하지 못한 채 복사해서 보낸다. 이 도구의 목적은
대신 써주는 게 아니라 **무엇을 요구받고 있는지 먼저 알게 하는 것**이다.

## 데이터 계약 — `POST /api/analyze`

**Request**

```json
{
  "maskedText": "{{PERSON_1}}님 주말에 미안한데, ...",
  "context": {
    "job": "기획·PM/PO", "level": "주니어", "counterpart": "직속상사",
    "goal": "칼차단", "tone": "보통맛", "hiddenContext": "가족 행사로 외지에 있음"
  }
}
```

**Response**

```json
{
  "xray": {
    "subtext": "...", "powerAsymmetry": 4,
    "urgencyType": "주말 침범", "ambiguityType": "범위 불명",
    "aiSlopScore": 0, "clicheHits": ["시간 날 때", "가볍게", "급한 건 아니"],
    "sentenceCount": 3, "hasNumbers": false, "hasDeadline": false, "avoidsDecision": true,
    "aiReported": { "...": "AI가 보고한 원본 (검증용)" }
  },
  "replies": [{ "label": "목적 맞춤형 정밀 방어", "text": "{{PERSON_1}}님, ..." }],
  "risk": { "score": 92, "level": "red", "label": "심각", "header": "고위험 독박 경보", "breakdown": [] },
  "usage": { "input_tokens": 0, "output_tokens": 0 },
  "meta": { "mode": "mock", "model": "mock", "latencyMs": 3 }
}
```

- **AI는 `riskScore` 를 반환하지 않는다.** `risk` 는 서버의 룰엔진이 계산한 값이고,
  클라이언트도 같은 모듈(`src/lib/score.js`)로 재현할 수 있다.
- 클리셰·수치·기한·의사결정 회피는 **규칙 계산값을 채택**하고, AI가 보고한 값은
  `xray.aiReported` 에 남겨 대조할 수 있게 둔다. AI가 지어낸 클리셰는 원문 대조로 걸러진다.
- 답장 텍스트에는 마스킹 토큰이 그대로 들어 있고, 브라우저가 렌더링 직전에 역치환한다.

## 룰엔진

```
Social Risk Index = 권력 비대칭(0~40) + 시간적 긴급도(0~20) + 요구 모호성(0~20) + 알맹이 결여율(0~20)
  권력 비대칭 = powerAsymmetry(1~5) × 8
  시간적 긴급도 = urgencyType ≠ "없음" → 20
  요구 모호성 = ambiguityType ≠ "없음" → 20
  알맹이 결여율 = (클리셰 밀도 + 수치·기한 부재 + 의사결정 회피) / 3 × 20
```

**정상 업무 가드**: 긴급도·모호성이 모두 "없음" 이고 결여율이 0이면 점수는 Green 상한(20)을
넘지 않는다. 과잉 방어는 제품 신뢰를 깎기 때문이다 (골든 ⑤ 대조군 검증 조건).

한글 사전 매칭은 NFD(자모 분해) 기준이다. `"아니"` 는 `"아닙니다"` 의 부분문자열이 아니라서
음절 그대로 비교하면 사전이 헛돈다.

# 개발 기록 (부록)

아래는 스프린트별 작업 로그다. **무엇을 만들었는지보다 "왜 그렇게 바꿨는지"** 를
남기는 데 목적이 있다 — 실사용 피드백으로 방향을 튼 지점, 실측으로 가설이 틀렸다고
확인한 지점, 고치지 않고 남겨둔 한계와 그 이유가 함께 적혀 있다.

### 입력 흐름 — 상황 카드는 예시를 "보여주기"만 한다 (채우지 않는다)

`② 구체적인 상황` 카드는 이제 **아무 값도 실제로 채우지 않는다.** ③ 입력창의
`placeholder`(연한 회색 예시 텍스트)를 바꿀 뿐이다 — 입력을 시작하는 순간 브라우저가
자동으로 지워주는, 진짜 "예시"다.

처음엔 메시지를 실제로 값으로 채워 넣었는데("① 맥락 매트릭스는 손대지 않는다" 버전으로
한 차례 수정한 뒤에도) 여전히 "프리셋처럼 다 채워지는 느낌"이라는 피드백을 받았다.
실제 값을 채우는 한, 아무리 다른 필드를 안 건드려도 "이미 완성된 답을 넣어주는 도구"처럼
보인다 — 예시는 어디까지나 "이런 느낌의 내용이 오갈 수 있다"는 참고이지, 사용자가 그대로
제출할 답이 아니다. 그래서 실제 채워넣기(fill) 대신 미리보기(placeholder)로 바꿨다.

- 카드 클릭 → `#message` 의 `placeholder` 속성만 바뀐다. `value`(실제 입력값)는 계속 비어 있다.
- 타이핑을 시작하면 예시는 그냥 사라진다 — 별도 처리 없이 HTML `placeholder` 의 기본 동작이다.
- 값이 비어 있는 채로 `실행`을 누르면 "상황 카드는 예시일 뿐, 직접 입력해야 분석됩니다"
  라고 안내한다.
- ① 맥락 매트릭스·④ 숨은 속사정·⑤ 방어 목적·⑥ 완곡도는 여전히 손대지 않는다(이전 수정 유지).

> **프리셋 캐싱에 대한 영향**: 이제 카드 클릭이 `message` 값조차 채우지 않으므로, 아래
> "프리셋 0초 캐싱"은 사용자가 예시 문구를 토씨 하나까지 그대로 타이핑하고 나머지 필드까지
> 골든 값과 우연히 일치시키지 않는 한 사실상 트리거되지 않는다. 캐시 로직·테스트(`test/presets.test.js`)는
> 여전히 유효하고 통과하지만, **지금 UI 흐름에서는 실사용 경로가 아니다.**
>
> **결정: 걷어내지 않고 유지한다.** 유저별로 결과를 따로 저장해야 하는 케이스(로그인/개인화가
> 들어오는 시점)를 대비한 기반으로 남겨둔다 — `PRESET_CACHE` 는 지금은 "id → 정적 JSON"
> 조회이지만, 나중에 "id → 사용자별 저장값" 조회로 바꿔도 `matchPresetId()` 이후의 렌더링
> 경로(`buildResult` 호출부)는 그대로 재사용할 수 있는 구조다. 지금 당장 로그인·DB를 들이는
> 건 아니다(가이드 §12 "하지 않을 것"과 상충하지 않음) — 코드를 지우지 않고 놔둔다는 결정일 뿐,
> 새 기능을 지금 만드는 것은 아니다.

## Sprint 2 — 영수증 카드 · 원티드 넛지 · 모바일 · 엣지케이스

### 1) 오피스 방어 영수증 (가이드 §3.3)

결과가 나오면 `③ 영수증 발급` 버튼이 뜬다. 클릭하면 종이 영수증 느낌의 카드가

처리가 안정적).

**카드에 들어가는 값과 계산 근거** (`src/lib/receipt.js`, 전부 순수 함수·전부 테스트됨):

| 항목 | 계산 방법 |
|---|---|
| 방어 대상 직무 | `context.job (context.level)` — 그대로 표시 |

| 적용 방어 모드 | 목적×완곡도 조합 라벨 (`칼차단`+`매운맛` → "🛑 여지없는 칼차단" — 가이드 예시와 일치) |

| 이번 달 발급 건수 | 이 브라우저의 `localStorage` 카운터. 서버 전송·계정 동기화 없음(로그인이 없어서) — "이번 달 발급한 방어 영수증" 이라고 정확히 그 범위로 표기했다 |

> **결정 (전에는 "판단 필요"로 남겨뒀던 항목)**: "재미로 보는 지표"는 EAP 심리상담
> 링크가 바로 옆에 붙는 카드 맥락과 톤이 안 맞는다는 피드백을 반영해 **"심리적

## 실사용 테스트 피드백 반영 (Sprint 2 이후)

실제로 써보면서 나온 두 가지 문제를 재현·수정했다.

### 1) "대화를 복붙하면 잘 관리될까?" — 여러 턴 대화가 신호를 희석시킨다

같은 요청을 (a) 상대방 메시지 한 줄만 넣었을 때와 (b) 내 발화까지 섞인 대화록으로
넣었을 때를 비교하면 점수가 **51점(주의) → 16점(정상)** 으로 떨어진다 — 내가 쓴
"확인해볼게요" 같은 말이 섞이면서 룰엔진이 위험 신호를 놓친다. 룰엔진은 "누가 한
말인지" 구분하지 않고 텍스트 전체를 하나로 보기 때문이다.

화자 분리는 오탐 위험이 커서 시도하지 않았다 — 대신 **막지 않고 알려주는** 쪽을
택했다:

- `src/lib/thread-hint.js` (`looksLikeMultiTurnThread`): "나:", "내가:", "Me:" 같은
  자기 발화 마커, 또는 서로 다른 화자 라벨이 2개 이상 있으면 감지한다. 시각 표기
  (`14:00`, `오전 9시:`)나 단발성 헤더(`안건: ...`)는 라벨 1개뿐이라 오탐하지 않는다.
- ③ 입력창 아래에 항상 보이는 안내(`상대방이 보낸 부분만 넣어주세요`) + 감지되면
  뜨는 경고 배너, 두 겹으로 안내한다. 입력을 막지는 않는다 — 그래도 분석은 된다.

### 2) "카운터가 내 메시지를 다르게 표현한 것 같다" — MOCK 답장이 내용을 안 읽고 있었다

재현: 유관부서가 보낸 "데이터 스펙 공유 부탁드립니다" 메시지를 넣으면, [목적 맞춤형
정밀 방어] 답장이 "요구사항 정의가 선행되어야 착수 가능합니다"라며 **내용과 무관한
PM 용어**를 내놓고, [속마음 분노 세탁 버전]은 subtext 의 진단 문구("범위와 기한이
비어 있습니다")를 사실상 그대로 반복했다. 사용자가 정확히 짚은 문제였다.

원인: `mock.js` 의 답장 템플릿이 목적×완곡도로만 갈라지고, 룰엔진이 이미 진단한
`ambiguityType`(R&R 미지정/범위 불명/기한 불명)을 답장에 반영하지 않았다.

수정 (`src/lib/mock.js`):
- `ambiguityFocus(ambiguityType)` 가 진단 결과를 "담당 범위"/"작업 범위"/"마감
  기한" 같은 구체적 명사구로 바꾸고, 답장(선제적 아젠다 요구·속마음 분노 세탁·
  공넘기기 방어)이 이 명사구를 직접 언급하도록 고쳤다. subtext 의 원 문장은
  그대로 두고, 답장 쪽 표현만 다르게 써서 "재진술처럼 보이는" 문제를 없앴다.
- 조사(이/가, 을/를)를 한글 받침 유무로 직접 계산해 붙인다(`josaI`/`josaEul`) —
  "범위이(가)" 같은 병기 표기 대신 "범위가"/"기한이"처럼 자연스럽게 나온다.
- 결과 패널에 **"지금은 규칙 기반 예시 답장입니다(MOCK)"** 안내를 추가해, 실제
  LIVE 모드(Claude 호출)에서는 메시지 내용을 읽고 쓴 답장이 나온다는 걸 명확히
  했다 — MOCK 의 한계를 사용자가 오해하지 않게.

```
[선제적 아젠다 요구] 수정 전: "진행 전 네 가지만 확정하고 싶습니다. (1) 최종 산출물 ..."
[선제적 아젠다 요구] 수정 후: "마감 기한이 명확하지 않아 진행 전 네 가지만 확정하고 싶습니다. (1) 최종 산출물 ..."

[속마음 분노 세탁] 수정 전: "이번 요청은 범위와 기한이 비어 있어, 이대로 진행하면..." (모든 케이스 동일)
[속마음 분노 세탁] 수정 후: "이번 요청은 마감 기한이 정해지지 않은 채로 왔습니다. ..." (R&R 미지정이면 "담당 범위"로 바뀜)
```

`test/reply-quality.test.js` 로 (1) 답장이 subtext 문구를 그대로 복사하지 않는지,
(2) 서로 다른 ambiguityType 을 유발하는 메시지끼리 답장의 초점 명사도 실제로
달라지는지 검증한다. 테스트 76 → 86개.

> 근본적으로는 MOCK 이 "감으로 그럴듯하게 흉내" 내는 규칙 기반 근사치라서, 완전한
> 내용 이해는 LIVE 모드(실제 Claude 호출)에서만 가능하다. 이번 수정은 MOCK 을
> LIVE 처럼 만든 게 아니라, MOCK 이 최소한 "무엇이 비어 있는지"는 답장에 반영하게
> 만들고 그 한계를 화면에 정직하게 알린 것이다.

### 3) "③에 붙여넣으면 ②를 추천해주는 게 더 자연스럽지 않을까?" — 카드 우선 → 입력 우선으로

기존 흐름은 "② 카드를 먼저 훑어보고 비슷한 걸 고르면 ③에 예시가 뜬다" 였다. 하지만
실사용자는 대부분 이미 손에 문제의 메시지를 들고 있다 — ③에 바로 붙여넣는 게
자연스러운 시작점이고, ②는 그 다음에 "아, 이런 케이스였구나" 확인하는 용도에 더
가깝다.

그래서 방향을 뒤집지 않고 **더했다**: ③에 타이핑(또는 붙여넣기)하면, 이미 있는
규칙 기반 신호(urgencyType/ambiguityType/aiSlopScore)로 ②의 8개 카드 중 가장
비슷한 것에 `✨ 비슷해요` 표시만 얹는다. 카드 클릭 시 예시를 보여주는 기존 동작은
그대로 둔다 — 자동으로 아무것도 채우거나 강제 선택하지 않고, 힌트만 준다는 원칙
(applyPreset 관련 이전 수정들)과 일관된 형태다.

- `src/lib/cliche.js` — `detectUrgency`/`detectAmbiguity`/`aiSlopScore`/
  `AI_SLOP_MARKERS` 를 `mock.js` 에서 이쪽으로 옮겼다. MOCK 분석과 실시간 카드
  추천이 같은 규칙 신호를 중복 없이 재사용하게 하기 위해서다("AI는 추출, 판정은
  규칙" 원칙에서 이 부분은 순수 규칙이라 위치만 옮겼고 판단 로직은 바뀌지 않았다 —
  기존 94개 테스트가 그대로 통과함으로 확인).
- `src/lib/situation-match.js` (`matchSituationId(text, counterpart)`) — 위
  신호들을 receipt.js 의 `villainType()` 과 같은 형태의 우선순위 캐스케이드로
  엮어 카드 id 하나 또는 `null` 을 돌려준다. 8개 카드 원문을 각각 다시 넣었을 때
  전부 자기 자신으로 매칭되는지 테스트로 고정했다(`test/situation-match.test.js`).
- `src/main.js` — 입력마다(디바운스 350ms) 최소 8자 이상일 때만 판단하고, 상대방
  칩(counterpart)을 바꿔도 즉시 재판단한다. 원문은 로컬 판단에만 쓰이고 네트워크로
  나가지 않는다(마스킹 전 텍스트를 서버로 보내지 않는다는 원칙과 무관 — 애초에
  전송 자체가 없다).
- 짧은 입력·신호 없는 평범한 메시지는 추천을 띄우지 않는다(노이즈 방지). 테스트
  99개로 확장.

### 4) 모바일 UX 검토 — 실측 스크린샷으로 터치 타겟·확대 버그 확인

전체 UX 검토(페이지 분리·CTA 배치·디자인 디테일) 중 모바일(375px) 실기기 조건을
Playwright 로 직접 재현해 두 가지를 실측했다:

- **iOS Safari 자동 확대**: `textarea`/`input[type=text]` 폰트가 14px 라서, iOS
  Safari 는 16px 미만 입력 필드에 포커스가 가면 페이지를 강제로 확대한다. ③
  메시지 입력창을 탭할 때마다 화면이 튀는 문제였다.
- **터치 타겟 미달**: 실측 높이가 칩 31px, 상황 카드 41px — 애플/구글 가이드라인
  권장 최소치(44px)에 못 미쳐 오탭 위험이 있었다.

`@media (max-width: 920px)` 안에서만(데스크톱 밀도는 그대로) 수정했다 — 칩
44px·카드 46px·복사 버튼 38px 로 올리고, 입력 필드 폰트를 16px 로 키웠다.
수정 후 같은 스크립트로 재측정해 칩 44px·카드 46px·가로 스크롤 없음을
확인했고, 데스크톱 스크린샷은 수정 전후 픽셀 단위로 동일함을 확인했다(920px
초과 구간은 건드리지 않았으므로).

### 5) CTA 배치 고도화 — 스크린샷 실측으로 확인한 두 가지를 수정

같은 UX 검토에서 나온 "결과 패널이 스크롤 중 화면 밖으로 밀려난다"는 가설을
DOM 실측(`boundingBox`)으로 다시 확인해보니, 처음 진단(패널 전체가 큰 빈
박스로 보임)은 과장이었다 — 실제로는 짧은 대기 패널의 둥근 모서리 한 조각만
살짝 보이는 정도였다. 대신 진짜 문제는 다른 곳에 있었다:

- **결과 스크롤 타겟이 틀렸다**: 실행 후 `el.result.scrollIntoView({block:
  'nearest'})` 가 패널 전체를 기준으로 삼다 보니, 정작 제일 중요한 위험
  점수·경보 헤더가 화면 위로 잘리고 진단 설명문부터 보였다(스크린샷으로
  확인). `el.xray.scrollIntoView({block:'start'})` 로 바꿔 점수·경보가
  항상 먼저 보이게 했다.
- **영수증 버튼이 실제 중요도보다 얕아 보였다**: 점선 테두리는 관례적으로
  "덜 중요한 옵션"으로 읽히는데, 이 버튼은 사실 공유·바이럴 루프의 핵심
  CTA다. 실선 + 강조색 배경으로 격상했다.
- **데스크톱 결과 패널을 `position: sticky` 로 고정**했다(920px 초과 구간만).
  입력 폼을 내려가며 채우는 동안 결과 패널이 항상 시야에 머물러서, 위 스크롤
  보정 로직 자체가 데스크톱에서는 거의 필요 없어진다(이미 보이므로).

### 6) 단계 그루핑 — 페이지 분리 없이 진행감만 주기

"번호별로 페이지를 나눌까?" 검토 결과는 **비분리**였다 — ③에 입력하면 ②를
실시간 추천하는 상호작용이 동시 노출을 전제로 하고, 모바일 전체 스크롤도
이미 짧은 편이라 페이지 분리의 이득이 크지 않았다. 대신 라우팅 없이 시각적
그룹핑만 추가했다: `①②③`→"1 상황 입력", `④⑤⑥`→"2 답장 설정", `⑦`→"3 실행"
세 구간에 작은 원형 배지 + 구분선(`.step-divider`)을 얹었다.

(이후 7번 항목에서 블록별 ①~⑦ 원문자 자체는 제거했다 — 시퀀스 정보를 이제
step-divider 가 담당해서 둘이 겹치는 중복 번호매김이 됐기 때문. id·기능은
그대로다.)

### 7) "AI 슬롭 없이 유려하게" — 색·아이콘·라운드값 정리

시중 서비스와 톤을 맞춰달라는 요청에 참고 사이트(throneinvest.ai)를 붙이려
했지만 이 개발 환경의 네트워크 정책상 접근이 막혀있어(EGRESS_BLOCKED) 실물을
보지 못했다 — 대신 "AI 생성 디자인이 클리셰로 굳어진 패턴이 뭔지"를 기준으로
현재 화면을 실측 점검했다. 두 가지가 정확히 그 클리셰에 해당했다:

- **"거의 검은 배경 + 형광 그린 포인트 컬러"** — 정확히 지금 배색이었다
  (`--bg:#0b0f16` + `--accent:#3ddc97`). 더 나쁜 건 이 초록이 위험도
  "안전" 등급의 `--green` 과 **같은 값**이었다는 점 — 브랜드색(칩·버튼 등
  UI 크롬)과 "지금 위험도가 낮다"는 의미가 우연히 뒤섞여 있었다.
- **"이모지를 섹션 마커로 쓰기"** — 🚨💡⚠️🛡️📁🧾💬 등 UI 곳곳에 장식용
  이모지가 붙어 있었다. 카드 그리드의 카테고리 이모지(📅🤖🏓👑 등, 8개 중
  하나를 빠르게 스캔하게 도와줌)나 톤/목적 칩의 🟢🟡🔴·🛑⏳🏓🕊️ 같은 건
  실제로 정보를 나르는 기능성 이모지라 남겼지만, 헤더·배지·버튼에 붙은
  나머지는 순수 장식이었다.

수정:
- **브랜드색 분리**: `--accent`/`--accent-dim` 을 초록(`#3ddc97`)에서
  파랑(`#4f8cff`/`#2f5fc2`)으로 바꿨다. 위험 등급 색(`--green`~`--red`)은
  손대지 않아 이제 "브랜드"와 "위험도 낮음"이 우연히 같은 색으로 안 읽힌다.
  칩·프리셋 선택 상태·링크·실행 버튼·영수증 버튼 등 하드코딩돼 있던
  `rgba(61,220,151,*)` 값도 전부 같은 파랑으로 맞췄다(리스크 계산 로직인
  `score.js`/`receipt.js` 는 전혀 건드리지 않았다 — 색상은 순수 표현 계층).
- **장식용 이모지 제거, 상태는 색·모양으로 표현**: 위험 경보 헤더는 이모지
  대신 등급 색을 그대로 물려받는 작은 점(`::before`)으로, 진단 설명(subtext)
  칸은 아이콘 대신 좌측 강조선(accent bar)으로, 경고 문구는 `⚠️` 대신 굵은
  리드 문구("여러 화자 감지 —", "관계 비용 경고 —")로 바꿨다. 방화벽
  브랜드 마크(🛡️)는 하나의 인라인 SVG 쉴드 아이콘으로 통일해 대기 화면과
  ③ 배지에서 똑같이 쓴다 — 이모지 렌더링이 OS·폰트마다 달라지는 문제도
  같이 없앤다.
- **①~⑦ 원문자 제거**: step-divider(1/2/3)가 이미 "이건 순서가 있는
  흐름"이라는 정보를 담당하는데, 블록마다 ①~⑦를 또 붙이면 같은 정보를
  두 번 표시하는 셈이었다(제출 체크리스트에도 없는 군더더기). 블록
  제목에서만 제거하고 id·기능은 그대로 뒀다.
- **라운드값 위계화**: 모든 카드가 똑같이 `border-radius:12px` 라 위계가
  안 보였다. `--radius-sm(8px)`/`--radius(12px)`/`--radius-lg(18px)` 세
  단계로 나눠 실행 버튼·X-Ray 결과 카드처럼 "제일 중요한 표면"에만
  `--radius-lg` 를 쓰고, 답장 카드 같은 반복 요소는 기존 `--radius` 를
  유지했다.

## 나의 방어 기록 (로컬 히스토리)

### 배경 — 이 도구를 쓰는 사람이 실제로 원하는 것

"오늘 내가 무슨 얘기 들었는지 알아?" 하고 누군가에게 털어놓고 싶을 때, 또는
상황·관계 때문에 반발 없이 그대로 받아들이고 일해야 할 때 — 둘 다 "이게 실제로
몇 번이나 있었는지, 얼마나 위험한 신호였는지"를 스스로에게 증명해 줄 기록이
필요하다. 지금까지의 화면은 "이번 한 건"만 보여줬지, 누적된 패턴은 안 보여줬다.

### 구현

우측 상단 `📁 나의 방어 기록` 버튼으로 언제든 열 수 있다. 실행할 때마다
카테고리·점수만(원문 없음) `localStorage` 에 쌓인다 — 영수증(receipt.js)과
정확히 같은 원칙이다: `entryFromResult()` 는 `xray.subtext`/`clicheHits`/
`maskedText`/`replies` 를 아예 읽지 않고, 이미 계산된 `villainType`·
`defenseModeLabel`·점수만 뽑는다.

- 요약: 총 기록 수, 평균 위험 지수, 가장 흔한 빌런 유형.
- 목록: 최신순, 점수·빌런 유형·날짜·직군·방어 모드.
- `전체 삭제` — 확인 후 완전히 지운다. 최대 200건 보관, 넘으면 오래된 것부터 버린다.
- **서버 전송 없음, 계정과 무관.** 브라우저를 바꾸거나 데이터를 지우면 사라진다 —
  로그인이 없는 이 프로젝트의 제약(가이드 §12) 안에서 할 수 있는 가장 정직한 형태다.

`test/history.test.js` 로 검증: 최신순 정렬, 200건 상한, 손상된 JSON 복구,
요약 통계 계산, 그리고 **원문 필드를 저장 시점에 아예 참조하지 않는지**까지
확인한다.

### 비즈니스 모델 아이디어 검토 — "이 기록을 기반으로 개인화된 프롬프트 제공"

제안: 누적된 로컬 기록을 바탕으로 사용자별 시스템 프롬프트(자주 겪는 빌런 유형,
선호하는 톤 등을 반영)를 따로 관리해 주는 걸 유료 기능으로 고려할 수 있지 않을까.

방향성은 타당하다고 본다 — 다만 지금 저장 방식 그대로는 부족하다:

- 지금 로컬 기록은 **의도적으로 카테고리·점수뿐**이라(원문 없음), 실제로 "이
  사람은 이런 어조의 상사를 자주 만난다" 같은 맥락 있는 개인화 프롬프트를
  만들기엔 재료가 너무 적다. 진짜 개인화를 하려면 원문(또는 마스킹된 원문)까지
  누적해야 하는데, 그건 지금의 "브라우저에만, 서버 전송 없음" 원칙과 정면으로
  부딪힌다.
- "별도 프롬프트로 따로 관리"는 사실상 **계정(로그인) + 서버 저장**을 전제로
  한다 — 기기를 바꿔도 유지되고, 결제와 연결되려면 사용자 식별이 필요하다.
  가이드 §12 "하지 않을 것"(로그인·DB·사용량 로그 저장)과 정확히 충돌한다.
  즉 이건 **이번 해커톤 스코프가 아니라 그 다음 단계(v2) 제품 방향**이다.

그래서 지금은 다음 형태를 제안한다: 로컬 기록은 지금처럼 무료·프라이버시
우선으로 계속 두고, **"내 기록을 서버에 안전하게 백업하고, 그걸 바탕으로 개인화된
방어 전략을 받아보세요"** 같은 명시적 옵트인 유료 티어를 v2 로 분리하는 것.
사용자가 "내 데이터를 서버로 보내겠다"고 분명히 동의하는 순간부터 계정·과금이
자연스러워지고, 지금 이 무료 버전의 "원문을 절대 안 보낸다"는 신뢰는 그대로
지켜진다. 제출 폼/피치에는 "로컬 우선 무료 버전 + 옵트인 개인화 유료 티어"라는
확장 로드맵으로 넣기를 제안한다 — 지금 코드로 만들지는 않았다.

## LIVE 경로 점검 (실행된 적 없던 코드 검증)

지금까지 모든 검증은 MOCK 경로로만 이뤄졌다. `ANTHROPIC_API_KEY` 가 없으면
`shouldUseMock()` 이 true 라서, **실제 모델을 호출하는 코드는 단 한 번도 실행된
적이 없었다** — 시연 당일 키를 꽂는 순간 처음 돌아가는 코드였다는 뜻이다.
API 규약 문서와 대조해 점검한 결과 버그 3건을 찾아 고쳤다.

### 1) 출력 상한(2048)이 JSON 을 자를 수 있었다

Claude Opus 5 는 thinking 이 **기본으로 켜져 있고**(adaptive), thinking 토큰도
`max_tokens` 를 함께 소진한다. 기존 `max_tokens: 2048` 로는 사고 과정에 예산을
쓰고 나면 JSON 이 중간에 끊길 수 있었고, 그러면 `extractJSON` 이 실패해
502(UPSTREAM_FAILED)로 떨어진다. → `16000` 으로 올렸다. 실제 응답 길이는
`output_config.effort: 'low'` 로 조인다(상한을 올려도 평소 비용은 늘지 않는다).

### 2) 재시도 × 타임아웃이 Vercel 함수 제한을 넘었다

SDK 의 `maxRetries` 기본값은 2이고 **타임아웃도 재시도 대상**이다. 즉 최악의
벽시계 시간이 `12s × 3 = 36s` 인데 `vercel.json` 의 `maxDuration` 은 15s 였다 —
플랫폼이 함수를 먼저 죽여서 우리 JSON 에러 대신 불투명한 504 가 나가는 구조였다.
→ `maxRetries: 1`, 타임아웃 9s, `maxDuration: 25s` 로 정렬했다(9×2=18s < 25s).

### 3) `output_config` 400 이면 무조건 재시도하던 폴백 제거

"이 파라미터를 지원하지 않는 환경이면 옵션 없이 재시도" 하는 코드가 있었는데,
`effort` 는 이미 GA 파라미터라 전제가 틀렸다. 게다가 **모든 400 을 삼켜서**
잘못된 키·모델명 같은 진짜 오류에도 한 번 더 호출해 지연만 2배로 늘렸다. 제거하고
타입 있는 에러가 그대로 드러나게 했다.

### 추가: 실패 유형을 구분해서 보고한다

기존에는 거절·빈 응답·잘린 응답이 전부 "JSON 을 찾지 못했습니다" 하나로 뭉개졌다.
`stop_reason` 을 content 보다 먼저 확인하도록 바꿔 `MODEL_REFUSED` /
`EMPTY_MODEL_OUTPUT` / `MODEL_OUTPUT_TRUNCATED` 로 분리했다 — 로그만 보고 원인을
알 수 있다. 세 경우 모두 클라이언트는 기존대로 로컬 룰엔진으로 폴백한다.

### 테스트 (99 → 114개)

`test/live-path.test.js` — 모델 호출부에 가짜 클라이언트를 주입해 **실호출·API 키
없이** LIVE 경로를 검증한다:

- `extractJSON`: 코드펜스·잡담 혼입·문자열 속 중괄호·잘린 JSON·JSON 없음
- `stop_reason` 분기: refusal / 빈 응답 / max_tokens 잘림
- 요청 파라미터 회귀 고정: 출력 상한이 충분한지, effort, 캐시 브레이크포인트,
  **타임아웃이 maxDuration 보다 작은지**(위 2번 버그의 재발 방지)
- 설계원칙 회귀: 모델이 `riskScore` 를 우겨넣어도 점수는 규칙이 계산하는지,
  모델이 지어낸 클리셰가 원문 대조로 걸러지는지, 필드 누락 시 폴백이 버티는지
- LIVE 경로에서도 원문 PII 가드가 **모델 호출 이전에** 동작하는지

### 아직 남은 것

- **실측은 여전히 불가**: 실제 토큰/비용/지연시간은 키를 꽂고 한 번 돌려봐야
  나온다. 위 수정은 "규약과 어긋난 부분"을 고친 것이지 실측을 대체하지 않는다.
- **프롬프트 캐시가 실제로 먹는지 미확인**: 시스템 프롬프트가 약 1K 토큰인데
  모델별 최소 캐시 프리픽스(512~4096 토큰)에 미달하면 `cache_control` 이 조용히
  무시된다. 키 투입 후 `usage.cache_read_input_tokens` 가 0 인지 확인할 것.
- **구조화 출력(structured outputs) 미적용**: `output_config.format` 으로 스키마를
  강제하면 `extractJSON` 자체가 필요 없어진다. 다만 의존성(zod)이 늘고 호출
  형태가 바뀌는데 **지금은 검증할 방법이 없어서**(키 없음) 넣지 않았다 — 키가
  생기면 우선 검토 대상.

## 보안 검토

제품의 핵심 주장이 "원문은 브라우저를 벗어나지 않는다"이므로, 마스킹 커버리지와
남용 방지는 부가 기능이 아니라 신뢰의 전제다. 전체 코드를 기준으로 점검했다.

### 확인 결과 — 설계대로 지켜지고 있는 것

- **전송 페이로드에 원문이 없다.** `{ maskedText, context }` 뿐이고 `context` 는
  칩 선택값(enum) + **마스킹된** hiddenContext 다. 토큰 맵은 전송·저장되지 않는다.
- **XSS 안전.** 답장 텍스트는 역치환으로 실명이 복원된 뒤 DOM 에 들어가는데,
  `innerHTML` 이 아니라 `textContent` 로 넣는다. 나머지 보간 지점은 전부
  `escapeHtml()` 을 거친다.
- **로컬 기록·영수증에 원문이 없다.** 카테고리·점수만 저장하며, 정적 검사 테스트가
  `subtext`/`clicheHits`/`maskedText`/`replies` 접근을 막고 있다.
- **서버 로그에 본문이 없다.** 길이·지연시간·토큰 사용량·점수만 기록한다.

### 고친 것

**1) 이름 마스킹이 "이름+님" 형태만 가리고 있었다 (가장 큰 발견)**

실제로 돌려본 결과, 흔한 실무 표기 중 상당수가 **원문 그대로 모델로 나가고 있었다**:

| 입력 | 검토 전 | 검토 후 |
|---|---|---|
| `박지훈님 확인 부탁` | 가림 | 가림 |
| `김철수씨 이거 언제까지` | **노출** | 가림 |
| `박지훈 책임이 검토 중` | **노출** | 가림 |
| `이수진 팀장 보고 건` | **노출** | 가림 |
| `최영호 부장님께 보고` | **노출** | 가림 |

호칭 `씨/군/양` 과 **"이름 + 직급(님 없음)"** 패턴을 추가했다. 직급 자체는 그대로
남긴다 — `{{PERSON_1}} 팀장` 처럼 둬야 권력 비대칭 신호가 보존되기 때문이다.

오탐 방향이 안전하다는 점을 기준으로 삼았다: **이름이 아닌 걸 가리는 건 과보호지만,
못 가리는 건 유출이다.** 실제 업무 문장 16종으로 오탐을 측정해 "오늘 날씨",
"마케팅 대리점", "고객사 미팅", "대표님 보고" 등이 그대로 유지되는 것을 확인했다.

**2) 유료 엔드포인트에 서버측 제한이 전혀 없었다**

`/api/analyze` 는 호출마다 실제 모델 비용이 나가는데 제한이 **클라이언트 5초
쿨다운뿐**이었다 — curl 한 줄이면 우회되므로, 배포 URL 을 아는 누구든 API 예산을
소진시킬 수 있었다. `api/_lib/rate-limit.js` 를 추가해 IP 당 20회/분, 인스턴스
전체 200회/분으로 막고 `Retry-After` 와 함께 429 를 반환한다. 오래된 카운터 엔트리는
정리한다(안 하면 그 자체가 메모리 고갈 경로가 된다).

> 한계를 분명히 해둔다: 서버리스는 인스턴스마다 메모리가 따로라 이 카운터는 **인스턴스
> 단위**다. 스크립트 남용의 문턱을 크게 올리는 용도이지 엄밀한 전역 쿼터가 아니다.
> 엄밀한 제어가 필요하면 외부 저장소(KV 등)가 필요하다.

**3) UI 카피가 실제보다 많이 약속하고 있었다**

입력창 안내가 "이름·연락처·금액은 전송 전에 자동으로 가려집니다"라고 단정했는데,
위 1번대로 이름은 패턴 기반이라 완전하지 않다. 연락처·이메일·금액은 신뢰할 수 있으므로
그대로 두고, 이름은 "대부분"으로 정확히 바꾸고 **실제 안전장치인 "전송될 내용 확인"
미리보기를 안내에 노출**했다.

**4) 히스토리 렌더링의 이스케이프 누락** — `e.score` 가 이스케이프 없이 보간되고
있었다. localStorage 를 조작할 수 있어야 악용 가능하므로(= 이미 해당 오리진에서
코드 실행이 가능한 상태) 실제 위험은 낮지만, 비용이 0이라 막았다.

### 남아 있는 한계 (의도적으로 남김)

- **`지훈이가`(조사 직결), 영문 이름은 여전히 안 가려진다.** 이걸 잡으려면 "2~4글자
  한글 + 이/가" 같은 패턴이 필요한데, 일반 명사를 대량으로 오탐한다. 클라이언트
  정규식 NER 의 한계이고, 진짜 해법은 별도 NER 모델이다 — 지금 구조에서는
  **"전송될 내용 확인" 미리보기가 실질적인 최종 안전장치**다.
- **CSP 등 보안 헤더 미설정.** 앱에 인증·쿠키·세션이 없어 XSS 영향 범위가 self-XSS
  수준이고, `html-to-image` 가 data: URI 를 쓰기 때문에 엄격한 CSP 는 영수증 기능을
  깨뜨릴 수 있다. 적용한다면 배포 후 영수증 저장·복사를 반드시 재검증할 것.

`test/security.test.js` 12개로 위 항목을 회귀 고정했다 (테스트 114 → 126개).

> 남은 a11y 항목: `role="radiogroup"` 안의 칩들은 ARIA 규격상 화살표키 이동
> (roving tabindex)이 기대되지만 현재는 각각 Tab 으로만 이동한다. 조작은 가능하므로
> 치명적이지 않아 이번 범위에서는 두었다.

## 다크 → 라이트 테마 전환 (Wanted Montage 디자인 시스템 기준)

Claude Design 으로 만든 목업(핸드오프 zip)을 검토하는 과정에서 두 가지를 확인했다.

1. 핸드오프에 같이 첨부된 "디자인 시스템" 번들은 이 프로젝트와 무관한 다른
   프로젝트(토스 미니앱 "무더위 체감 랭킹")의 컴포넌트 목록(`HeatColorProvider`,
   `IconDroplet` 등)이었다 — 실수로 잘못 첨부된 것으로 판단, 참고하지 않았다.
2. 목업 자체는 라이트 테마였는데, 그 색상 11개 중 실제로 원티드 색과 일치하는 건
   2개뿐이었고, 나머지(특히 위험도 3단계 상태색)는 Tailwind 기본 팔레트였다 —
   "원티드 디자인 시스템"이라는 근거가 없었다.

근거 없는 팔레트를 그대로 쓰는 대신, 원티드가 공개한 실제 디자인 시스템
([`wanteddev/montage-web`](https://github.com/wanteddev/montage-web), MIT)의
토큰 소스(`packages/wds-theme/src/theme/{atomic,semantic}`)를 직접 클론해서 읽고,
그 값으로 앱의 `:root` 토큰을 다시 짰다.

| 토큰 | 이전 (다크) | 이후 (Montage 라이트) | 근거 |
|---|---|---|---|
| `--bg` / `--bg-panel` | `#0b0f16` / `#141c2b` 계열 | `#f7f7f8` / `#ffffff` | `coolNeutral[99]` / `common[100]` |
| `--text` / `--text-dim` | 밝은 회색 계열 | `#171719` / `#5a5c63` | `coolNeutral[10]` / `[40]` |
| `--accent` | `#4f8cff` | `#0066ff` | `blue[50]` (Montage 시그니처 블루) |
| `--green`/`--lime`/`--amber`/`--orange`/`--red` | Tailwind 기본값 | `atomic.{green,lime,orange,redOrange,red}[50]` | 위험도 5단계 색을 전부 실제 토큰으로 교체 |

가장 까다로웠던 부분은 **밝은 배경 위 가독성**이었다. Montage 는 같은 색상군에서
`accent.background`(칩 배경처럼 넓은 면적에 쓰는 밝은 톤)와 `accent.foreground`
(그 위에 얹는 텍스트/아이콘용, 더 진한 톤)를 분리해서 정의해 둔다. 이걸 그대로
적용해 `--amber-text`(`orange[39]` 계열), `--red-text`(`red[40]` 계열) 토큰을
추가하고, 경고 문구·칩 텍스트처럼 밝은 틴트 배경 위에 놓이는 글자는 전부 이
`-text` 변형을 쓰도록 바꿨다 — 그냥 `--amber`/`--red` 원색을 그대로 텍스트에
썼다면 흰 배경에서 대비가 부족했을 것이다.

예외적으로 유지한 것:
- **영수증 카드**(`.receipt-card`) — 종이 영수증 질감을 내려고 처음부터 크림/세피아
  톤으로 설계했던 부분이라 앱 테마와 무관하게 그대로 뒀다.
- **모달 백드롭**(`rgba(5, 8, 13, 0.72)`) — 오버레이 스크림은 관례상 테마와
  무관하게 어둡게 유지. 이 스크림 위에 직접 놓이는 EAP 링크 하나만 별도로
  `--accent-on-dark`(`blue[65]`, 어두운 배경에서 가독성 좋은 밝은 블루) 토큰을
  새로 만들어 적용했다 — 새 `--accent`(`#0066ff`)를 그대로 썼다면 짙은 스크림
  위에서 대비가 떨어졌을 것이다.

전환 후 `npx vite build` 성공, `node --test test/*.test.js` 130/130 통과(스타일링만
바꿨으므로 로직 테스트는 영향 없음), Playwright 로 대기 화면·X-Ray 결과(고위험/양호
양쪽)·영수증 모달·기록 모달을 라이트 테마로 재확인했다.

## "어떻게 작동하나요" 스텝탭 섹션 + CTA 카피 정리

원티드 이벤트 페이지(`2026_roadmap`) 레이아웃을 검토해달라는 요청이 있었는데,

배경만 참고 페이지의 "짙은 네이비 활성 탭" 느낌을 `--text` 토큰으로 재현했다.
`role="tablist"`/`role="tab"`/`role="tabpanel"` 로 마크업하고 방향키(←/→)로 탭
이동까지 지원한다.

같이 전달받은 원티드 카피 톤 분석(해요체, 질문형 후킹, "동사+하기" CTA, 공지

삭제"/"전송될 내용 확인"처럼 일부만 하기형이고 일부는 명사형으로 섞여 있던 걸
"복사하기"/"이미지로 저장하기"/"전체 삭제하기"/"전송될 내용 확인하기"로
맞췄다. 나머지 항목(해요체 전환, 문제→해결 3단 구조, 격식체/캐주얼 톤 분리)은

쓰고 있고(README "AI 슬롭 없이 유려하게" 절 참고), 공지·경고 문구는 원래도
격식체로 분리돼 있어 원티드 가이드의 4번·8번 체크리스트 항목은 이미 충족한
상태였다. 나머지를 억지로 해요체로 바꾸면 검증된 기존 카피 전체를 건드리는
큰 변경이 되는데 반해 톤 일관성 외의 실질적 이득은 없어서, 이번엔 CTA 통일만
반영했다.

## AI 제공자 전환 — Claude → Groq (제출 마감 직전, 비용 절감)

Sprint 0~2 는 전 구간 Anthropic Claude(`claude-opus-5`) 기준으로 만들었다.
제출을 앞두고 API 비용 부담 없이 진행하고 싶다는 요청이 있어 무료 티어가 있는
Groq(GroqCloud)로 실 호출 부분을 교체했다.

### 실제로 바뀐 부분

`api/_lib/analyze-core.js` 가 Anthropic Messages API(`client.messages.create`,
`content: [{type:'text'}]`, `stop_reason`) 대신 Groq 의 OpenAI 호환
chat.completions API(`client.chat.completions.create`, `choices[0].message.content`,
`finish_reason`)를 호출하도록 전면 재작성했다. `prompt.js`(시스템 프롬프트)는
특정 제공자에 종속된 지시문이 없어서 그대로 재사용했다.

| | 이전(Claude) | 이후(Groq) |
|---|---|---|
| SDK | `@anthropic-ai/sdk` | `groq-sdk` |
| 기본 모델 | `claude-opus-5` | `llama-3.3-70b-versatile` (env: `GROQ_MODEL`) |
| 환경변수 | `ANTHROPIC_API_KEY` | `GROQ_API_KEY` |
| 출력 형식 강제 | 프롬프트 지시만 | `response_format: { type: 'json_object' }` (API 레벨 보장) |
| 사용량 필드 | `usage.input_tokens`/`output_tokens` | `usage.prompt_tokens`/`completion_tokens` (내부적으로 같은 이름으로 매핑해 프론트는 무영향) |
| 프롬프트 캐싱 | `cache_control: ephemeral` | 없음(Groq 미지원) — `cache_*` 필드는 0 으로 고정, 하위 호환만 유지 |

### 추론(reasoning) 모델 노출 사고 — 겪기 전에 막아둔 것

Groq 무료 티어의 강한 모델(qwen3 계열, gpt-oss 계열)은 추론 모델이라 `<think>`
블록 형태로 사고 과정을 함께 뱉는 경우가 있다 — 이걸 그대로 노출하면 영어 사고
과정이 답장 내용에 섞여 나가는 사고로 이어진다(다른 프로젝트에서 실제로 겪은
문제라고 전달받았다). 이중으로 막아뒀다:

1. **API 레벨**: 요청에 `reasoning_format: 'hidden'` 을 넣어 서버가 아예
   reasoning 을 content 에 안 섞도록 한다(Groq 공식 문서화된 파라미터).
2. **방어선**: `analyze-core.js` 의 `stripReasoning()` 이 혹시 새어나온
   `<think>...</think>` 블록을 JSON 추출 전에 제거한다. `test/live-path.test.js`
   에 "reasoning 모델이 `<think>` 블록을 흘려도 JSON 은 정상 파싱된다" 테스트로
   고정해 뒀다.

### 배포 후 실측 — 무엇이 실제로 달랐나

개발 세션의 네트워크 정책이 `api.groq.com` 과 배포 URL 양쪽을 다 막고 있어서,
전환 코드는 **가짜 클라이언트 단위 테스트만 통과한 채로** 배포됐다. 실측은
배포 환경 안에서 골든 5종을 돌리고 결과만 GET 으로 돌려주는 임시 진단
엔드포인트(`/api/verify-live`, 검증 후 제거)로 했다. 그 결과 코드 리뷰나
타입 정의만으로는 알 수 없었던 것들이 한꺼번에 드러났다.

**1) 타입 정의에 있는 모델이 실제로 서빙되는 건 아니다.**
`groq-sdk` 의 타입 정의(`groq/groq-typescript`, Groq API 스펙에서 자동 생성)에
나열된 모델 14종 중 이 계정에서 실제로 응답한 건 **둘뿐**이었다.

| 모델 | 실제 응답 |
|---|---|
| `openai/gpt-oss-20b` · `openai/gpt-oss-120b` | ✅ 정상 |
| `llama-3.3-70b-versatile` · `llama-3.1-8b-instant` | ❌ 404 `model_not_found` |
| `moonshotai/kimi-k2-instruct` · `qwen/qwen3-32b` | ❌ 404 `model_not_found` |
| `gemma2-9b-it` | ❌ 400 `model_decommissioned` |

타입 정의를 근거로 `llama-3.3-70b-versatile` 을 기본값으로 골랐다가 전부
404 를 맞았다. 결국 처음 선택(`groq-sdk` README 예제가 쓰는 `openai/gpt-oss-20b`)
으로 돌아왔다. **교훈: 모델 목록은 라이브 호출로만 확정된다.**

**2) 추론 토큰이 무료 티어 한도를 태운다.**
gpt-oss 계열은 추론 모델이라 `reasoning_format: 'hidden'` 으로 사고 과정을
숨겨도 그 토큰이 출력 토큰으로 집계된다. 기본값에서는 호출당 출력이
1,100~2,800 토큰이었고, 골든 5종을 병렬로 돌리자 바로 429 가 났다 —
무료 티어 한도는 **8,000 TPM** 이다. `reasoning_effort: 'low'` 를 넣자:

| | 적용 전 | 적용 후 |
|---|---|---|
| 출력 토큰 | 1,100~2,800 | 340~740 |
| 응답 지연 | 2,990ms | 800~1,600ms |

이 작업은 정형화된 추출이라 low 로도 품질 저하가 관찰되지 않았다.

**3) 그래도 8,000 TPM 은 서비스 전체 한도다.**
호출당 입력 ~1,900 + 출력 ~600 ≈ 2,500 토큰이므로 **분당 약 3건**이 서비스
전체의 상한이다. 심사 기간에 여러 명이 동시에 쓰면 429 가 나고, 그때는
클라이언트가 로컬 룰엔진으로 폴백해 배지가 `오프라인 분석` 으로 바뀐다(화면이 비지는
않는다). 유료 전환 없이 이 구조를 쓰는 한 피할 수 없는 제약이다.

**4) 추출값이 호출마다 흔들린다 — 이게 가장 아픈 부분이다.**
같은 입력으로 연속 호출했는데 ④ 클라이언트 갑질이 36점과 67점으로 갈렸다.
`temperature: 0` 과 고정 `seed` 를 넣어도 ⑤ 정상 대조군이 36점/40점으로
흔들렸다 — Groq 의 결정성은 best-effort 다. 점수 계산 자체는 규칙이 하지만
그 입력이 되는 추출값이 흔들리면 **"같은 입력이면 항상 같은 점수"라는 이
제품의 핵심 주장이 화면에서 거짓이 된다.** Claude 시절에는 관찰되지 않던
문제다.

**5) 프롬프트 튜닝이 두더지잡기가 됐다 — 그리고 측정 자체가 틀렸었다.**
①(완곡어로 포장된 주말 근무 요구를 잡아야 함)과 ⑤(정상 메시지에 과잉 경보
금지)가 서로 밀어내는 사이클을 네 번 돌았다. 한쪽을 세게 지시하면 반대쪽이
무너졌고, "20B 모델의 능력 한계"라고 결론 내려 프롬프트를 되돌리기까지 했다.

그 결론이 틀렸다. Vercel 배포가 여러 개 겹쳐 도는 동안 **아직 반영되지 않은
빌드에 대고 측정하고 있었다.** 같은 시나리오의 `input_tokens` 가 호출마다
달라지는 걸 보고서야 알아챘다. `/api/verify-live` 응답에
`VERCEL_GIT_COMMIT_SHA` 를 넣어 "이 수치가 어느 빌드에서 나왔는지"를 응답만
보고 알 수 있게 고친 뒤 다시 재니, 되돌리려 했던 그 프롬프트가 **골든 5종을
전부 통과**했다.

> 교훈: 배포 파이프라인이 비동기인 환경에서 "방금 푸시했으니 지금 뜬 게 그
> 빌드겠지"는 측정이 아니라 추측이다. 빌드 식별자를 응답에 넣는 데 5분이
> 걸렸고, 그걸 안 해서 잘못된 커밋(`9b3f0ac` revert)을 하나 만들었다.

**최종 실측 (커밋 `bd18cb3`, `openai/gpt-oss-20b`):**

| 골든 시나리오 | 점수 | 등급 | 기대 구간 | 지연 | 토큰(in/out) |
|---|---|---|---|---|---|
| ① 주말 침범 | 84 | red | 61~100 | 1,250ms | 2,240 / 531 |
| ② AI 슬롭 | 48 | amber | 41~100 | 1,736ms | 2,195 / 863 |
| ③ R&R 핑퐁 | 64 | orange | 41~100 | 2,099ms | 2,185 / 654 |
| ④ 클라이언트 갑질 | 79 | orange | 61~100 | 20,073ms | 2,219 / 648 |
| ⑤ 정상 업무 대조군 | 8 | green | 0~20 | 1,288ms | 2,197 / 689 |

5종 모두 기대 구간 안에 들어왔다. 정상 대조군이 8점(green)으로 나온 게
특히 중요하다 — 과잉 경보를 안 한다는 게 이 제품의 신뢰 근거다.

**6) 그 "전부 통과"도 한 번의 표본이었다 — 그리고 원인을 하나 찾아 막았다.**
위 표를 찍고 진단 엔드포인트를 지우기 직전에 ⑤ 를 한 번 더 돌려봤더니, **같은
커밋·같은 입력인데 8점(green)이 아니라 40점(lime)** 이 나왔다. 과잉 경보를
안 한다는 게 이 제품의 신뢰 근거인데 그게 실행마다 뒤집힌 것이다.

원인은 `ambiguityType` 이었다. 설계원칙 1.1 에 따라 `clicheHits`·`hasNumbers`·
`hasDeadline` 은 이미 규칙값이 AI 값을 덮어쓰고 있었는데, 정작 점수를 20점씩
움직이는 `urgencyType`·`ambiguityType` 은 교차검증 없이 AI 값을 그대로 쓰고
있었다. 원칙을 적용하다 만 셈이다.

넷 중 "기한 불명"만은 원문에 날짜·시각이 있는지로 **사실 확인이 된다.** 규칙이
기한을 찾았는데 AI 가 기한 불명이라고 하면 환각이므로 버리도록 고쳤다
(`normalizeXray`) — 클리셰 환각을 원문 대조로 걸러내던 것과 같은 원리이고,
AI 원본은 `aiReported.ambiguityType` 에 남겨 감사할 수 있게 뒀다. "범위 불명"·
"R&R 미지정"은 규칙으로 검증할 방법이 없어 손대지 않았다. 회귀 테스트 4개를
붙였다(132 → 136).

> 다만 정직하게 남긴다: 이 수정은 **단위 테스트로만 검증했다.** 진단
> 엔드포인트를 이미 제거한 뒤라 라이브 재측정을 못 했고, ⑤ 가 뒤집힌 원인이
> "기한 불명" 하나였는지 "범위 불명"도 섞였는지는 확정하지 못했다. 즉 흔들림의
> 원인 하나를 결정론적으로 막은 것이지, 흔들림이 사라졌다고 말할 수는 없다.
> 시연에서는 점수를 못박기보다 등급(red/orange/green)으로 설명하는 게 안전하다.

④ 의 20초는 429 직후 SDK 자동 재시도가 TPM 창(약 15초)을 기다린 값이다.
`vercel.json` 의 `maxDuration` 25초에 아슬아슬하게 들어왔다. 연속 호출이
겹치면 여기서 함수가 죽을 수 있다 — 위 3) 의 처리량 상한이 실제로 물리는
지점이다.

### 전환 후 보안 재검토

제공자를 바꾸면 "원문은 AI 에 그대로 가지 않는다"는 이 제품의 약속이 깨지기
쉬우므로 전환 diff 를 따로 검토했다. 새로 유입된 취약점은 없다.

- `GROQ_API_KEY` 는 환경변수 → SDK 생성자로만 흐른다. 로그에도, 클라이언트로도
  나가지 않는다(`api/analyze.js` 의 로그는 mode·model·지연시간·글자수·토큰·점수뿐).
- 선-마스킹 가드(`detectRawPII`)는 **모델 호출 이전**에 그대로 동작한다. 제공자가
  바뀌어도 마스킹되지 않은 원문이 외부로 나가는 경로는 없다.
- 모델이 바뀌면 출력 문자열의 성격도 바뀌므로 렌더링 경로를 다시 봤다: `subtext`·
  답장 본문은 `textContent`, `clicheHits`·근거 표는 `escapeHtml`, `urgencyType`·
  `ambiguityType` 은 `pickEnum` 으로 열거값 제한, 숫자는 clamp. XSS 표면 없음.
- 검증용으로 잠시 띄웠던 `/api/verify-live` 는 토큰이 소스에 박힌 약한 가드였고,
  약 10분간 노출된 뒤 제거했다(404 확인). 엔드포인트가 사라졌으므로 그 토큰은
  더 이상 아무것도 열지 않는다.

### 왜 굳이 바꿨는가 — 비용 비교

`claude-opus-5` 기준 실제 호출 1회는 대략 $0.03~0.05 수준(짧은 정형 추출 작업이라
입력·출력 토큰 모두 적음, 위험 점수 자체는 규칙 엔진이 계산하므로 모델 몫은
사실 추출뿐)으로, 심사 기간 전체 사용량을 넉넉히 잡아도 큰 비용이 아니었다.
그럼에도 "무료로 진행하고 싶다"는 명확한 요청이 있었고, Groq 무료 티어가
실사용에 충분한 요청 한도를 제공해 교체했다. 제출 폼의 "사용 AI툴 및 기술
스택" 체크박스 목록(Claude/ChatGPT/Gemini/.../OpenRouter 등)에는 Groq 가
없어서 체크박스는 해당 사항 없음으로 두고, 자유 서술형인 "AI 활용 방식 및
결과" 항목에 Groq 사용 사실을 명시하기로 했다(`docs/SUBMISSION.md` 참고).

## 상황 카드 재설계 — 관계 8종 · 카드 10종 · 정렬에서 필터로

실사용 피드백이 한 문장으로 들어왔다. **"후배의 업무 떠넘기기가 후배를 골랐을 때만
나오거나, 아니면 그냥 업무 떠넘기기로 이름을 바꿔야 할 것 같다."** 이름 문제로
보였지만 실측해보니 원인은 로직이었다.

### 실측으로 확인한 문제 4가지

1. **`updatePresetOrder` 는 필터가 아니라 정렬이었다.** 관계를 무엇으로 고르든
   카드 10장이 전부 보이고 안 맞는 카드가 뒤로 밀리기만 했다. 라벨은 관계를
   주장하는데(`후배의 업무 떠넘기기`) 화면은 관계와 무관하게 다 보여주는 어긋남.
2. **`fits` 가 값 하나뿐이라** 관계 8종 중 6종은 "먼저 보여주는" 카드가 딱 1장이었다.
   2열 그리드에서 1장 순서가 바뀌는 건 사실상 보이지 않는다.
3. **`matchSituationId`(텍스트 매칭)가 반환 가능한 id 는 8개뿐이었다.** 나중에 추가한
   `juniordump`·`complainant` 는 **자기 예시 문구를 그대로 넣어도 절대 못 찾았다**
   (각각 `passthebuck`·`client` 로 오인, 자기 매칭 0/8).
4. **`nightowl`→선배, `groupchat`→임원 같은 재배정이 자의적이었다.** "빈 관계를
   채우려고" 배정한 것이지 실제와 맞지 않았다 — 야간 톡은 상사·선배·동기가 다 보낸다.

### 고친 것

**관계를 4종 → 8종으로.** `직속상사 · 임원 · 선배 · 후배 · 동기 · 타부서 동료 ·
클라이언트 · 민원인`. 기존 `팀원(AI복붙)` 은 관계 이름에 상황이 섞여 있어 제거했다.
점수에 영향을 주는 컨텍스트는 `counterpart` 하나뿐이므로(`POWER_BY_COUNTERPART`),
확장 시 권력 값만 정하면 된다 — 임원 5 · 클라이언트 5 · 직속상사 4 · 민원인 4 ·
선배 3 · 타부서 동료 3 · 동기 2 · 후배 1. `job`·`level` 은 표시·맥락 전용이라
넓혀도 점수 회귀 위험이 없다.

**`fits` 를 배열로 + 정렬이 아니라 진짜 필터로.** 관계당 매칭 카드가 1~2장 →
2~4장이 됐다. 안 맞는 카드는 `hidden` 으로 접고, `다른 상황도 보기 (+N)` 토글로
전체를 펼친다. 입력 텍스트가 접혀 있는 카드와 맞으면 필터를 자동으로 펼친다 —
관계는 클라이언트인데 야간 톡 문구를 붙여넣는 경우가 실제로 있기 때문이다.

**`matchSituationId` 라우팅을 10종 전부로.** `당일 마감 + 민원인 → complainant`,
`당일 마감 + 후배 → juniordump` 처럼 관계를 함께 보는 분기를 넣어, 이제 10장 모두
자기 예시 문구로 자기를 찾는다.

### 라벨 — "갑질"로 통일했다가 되돌린 기록

`fits` 가 배열이 된 이상 라벨에 관계 이름을 넣을 수 없었다("후배의 업무 떠넘기기"가
상사 화면에도 뜨면 이상하다). 그래서 한 번은 **"갑질"로 통일**했다. 관계 이름이
아니라 권력 남용이라는 *행위* 를 가리키는 말이라 여러 관계에 걸려도 논리적 모순은
없었고, 영수증의 빌런 네이밍("주말 도둑형")과 톤도 맞았다.

**그런데 10장 중 7장이 "OO 갑질"이 되자 목록 전체가 한 톤으로 눌렸다.** 카드 목록은
사용자가 "내가 겪은 게 이거다"를 찾는 갤러리인데, 거기서 먼저 필요한 건 평가가 아니라
**알아봄**이다. 낙인은 결과 화면의 영수증 빌런 유형이 이미 맡고 있어서 입력 단계에서
두 번 찍을 이유가 없었다. 그래서 **일어난 일 그대로** 부르는 쪽으로 다시 바꿨다.

### 한글 줄바꿈 — `word-break: keep-all`

라벨 교체 후 360px 에서 재보니 "주말 업무 요/청", "부서 간 떠넘/기기"처럼 어절
한가운데가 끊기고 있었다. 한글은 CSS 기본값(`word-break: normal`)에서 CJK 규칙이
적용돼 글자 단위로 접힌다. `.preset` 에 `word-break: keep-all` 을 줘 띄어쓰기에서만
접도록 하고, 띄어쓰기 없는 긴 낱말을 대비해 `overflow-wrap: break-word` 를 안전망으로
같이 뒀다(`keep-all` 만 두면 그런 낱말이 카드 밖으로 삐져나간다).

360px 실측: 10장 전부 가로 넘침 없음, 높이 62px 균일(2줄 이내).

## 기록 되살리기 · 영수증 정리 · 상황 × 관계 매트릭스

### 기록을 눌러 그때 결과로 돌아가기

"나의 방어 기록"은 목록만 보여줬다. 점수와 빌런 유형은 다시 보이는데
**"그때 뭐라고 답하기로 했더라"** 에는 답하지 못했다. 답장 3종이 이 도구의
산출물인데 기록에는 그게 없었다.

원문을 다시 불러오는 건 처음부터 불가능하다. `entryFromResult` 는 원문도
토큰 맵도 **인자로 받은 적이 없다**. 그래서 "다시 분석"이 아니라 "그때 화면을
다시 펼치기"로 만들었다. 엔트리에 `snapshot`(xray·risk·replies·context)을
얹고, 기록을 누르면 `render(..., { restored: true })` 로 같은 화면을 다시 그린다.
재분석하지 않는 이유는 따로 있다 — 기록은 그때 내린 판정을 보존하는 쪽이 맞다.

되살린 화면에는 이 세션의 토큰 맵이 없다. `unmask` 는 맵에 없는 토큰을 그대로
두므로 그냥 두면 답장에 `{{PERSON_1}}님` 이 날것으로 찍힌다. 저장 시점에 실명을
되돌려 넣는 건 기록이 실명을 갖게 되는 일이라 하지 않았고, 대신 보여줄 때만
중립 표기(`○○`)로 바꾼다(`showText`). 리로드 후 복원해 실측했다 — 답장 본문은
원래와 동일, 날것 토큰 노출 없음, `localStorage` 안에 실명 없음.

스냅샷은 최근 30건만 들고 있다(`MAX_SNAPSHOTS`). 200건 전부 들고 있으면 수백 KB가
되는데, `localStorage` 가 차면 조용히 실패하는 건 오래된 스냅샷이 아니라 **방금 만든
기록**이다. 떼어낸 기록도 목록과 통계에는 그대로 남고, 누를 수 없는 항목은 처음부터
버튼이 아니게 그린다.

`test/history.test.js` 의 가드는 바꿨다. 예전 테스트는 "xray 값이 엔트리에 하나도
없어야 한다"를 지켰는데 그건 목적이 아니라 당시의 구현이었다. 지켜야 할 불변식은
원문·실명이 들어가지 않는다는 것이고, 그건 **함수가 그 값을 받지 않는다는 구조**가
보장한다(`entryFromResult.length === 3`).

### 영수증 — 한글 mono 버그의 마지막 자리

"공유하고 싶은 형태가 아니다"의 원인은 `.receipt-card-inner { font-family: var(--mono) }`
였다. `--mono` 는 라틴 전용 스택이라 한글만 시스템 글꼴로 떨어지고, 같은 행에서
"주말 도둑형 상사"와 "+5.5 Hours"의 결이 서로 달랐다. 본문 전반에서 세 번 잡았던
버그인데 영수증만 "thermal print 느낌"을 이유로 예외로 남겨뒀던 자리다. 공유되는
이미지에서 이 불일치가 가장 크게 드러났다.

본문은 `--font` 로 통일하고 mono 는 라틴·숫자 전용 자리(브랜드·ISSUED AT·점수·URL)에만
남겼다. 영수증 특유의 결은 `tabular-nums` 와 자간이 대신 맡는다.

나머지 셋:
- **초점 하나.** 위험 지수가 다른 항목과 같은 크기의 행이라 카드에 초점이 없었다.
  54px 히어로로 세우고 판정 라벨(`scoreLabel`)을 함께 붙였다 — 계산해 두고 화면에
  쓰지 않던 값이다.
- **원티드 직접 링크.** 카드 안의 두 제안(원티드·EAP)은 이미지라 누를 수 없는데,
  모달에는 EAP 만 링크가 있었다. `wantedUrl(context)` 로 케어 블록과 같은 규칙
  (연차·직군)을 써서 원티드 링크를 나란히 뒀다.
- **출처.** 공유된 이미지에서 돌아올 단서가 없어 하단에 서비스 주소를 넣었다.

실측: 앱이 실제로 내보내는 PNG 760×1474, 모달 닫기 버튼은 카드 밖이라 포함되지 않음.

### 상황 카드 × 상대방 매트릭스

카드 하나가 여러 관계에 걸리는데(`fits`) 본문은 하나뿐이라, "주말 업무 요청"을
임원으로 고르든 선배로 고르든 **"대표님 보고가 잡혀서요"** 가 떴다. 선배는 그렇게
말하지 않는다. 예시가 자기 상황처럼 읽히지 않으면 카드를 눌러 볼 이유도 없다.

`byCounterpart` 를 얹어 11개 변형을 넣었다(21개 조합). 변형이 있으면 그걸,
없으면 기본 본문을 쓴다(`presetText`).

**변형은 문구만 바꾸는 게 아니라 신호까지 바꾼다.** 처음 쓴 11개 중 5개가 자기
카드로 매칭되지 않았다(실측):

- `"이렇게 늦은 시간에"` → `"이 밤에"` 로 줄이자 야간 침범 신호가 사라졌다
- 상투어를 덜어낸 AI 복붙 변형은 슬롭 점수가 기준선(60) 아래로 내려갔다
- `emailcreep` 변형은 문장 구조를 바꾸면서 `기한 불명` 이 `없음` 이 됐다

그 상태로 두면 카드에서 예시를 적용한 순간 "이런 상황인가요?" 힌트가 **다른 카드**를
가리킨다. 나머지 둘은 매처 쪽 문제였다. 클라이언트·민원인은 카드 세 장
(`client`·`emailcreep`·`complainant`)을 공유하는데 관계로만 갈라서, 민원인이면
무조건 `complainant` 였다. 관계 규칙보다 **먼저 내용을 보도록** 판별식을 넣었다 —
두 카드의 정체는 마감이 아니라 각각 "말이 바뀌고 추가 비용을 부정한다"와
"책임자를 호출하며 격앙돼 있다"에 있기 때문이다.

`PRESETS` 를 `src/data/presets.js` 로 분리했다. main.js 는 DOM 모듈이라 node 에서
import 할 수 없어 매트릭스를 테스트로 잠글 수 없었다. `test/preset-matrix.test.js` 가
21개 조합 전부와 "변형이 기본의 복사본이 아닌지", "실명·줄표가 없는지"를 고정한다.

테스트 165 → **170개**, 전부 통과.


## 공유 카드(OG)와 홈 화면 추가(PWA)

둘 다 **런타임에 확인할 방법이 없는** 기능이다. 조건이 깨져도 화면에는 아무
증상이 없고, 링크를 공유했을 때 이미지가 안 뜨거나 설치 버튼이 영영 안 나올
뿐이다. 그래서 `test/share-and-pwa.test.js` 로 파일 내용을 직접 고정했다.

### 공유 카드 — 카카오톡이 까다로운 지점

`public/og.png`(1200×630)를 굽고 `index.html` 에 OG/Twitter 태그를 넣었다.
원본은 `docs/assets/og.html` 이고 `node scripts/make-og.mjs` 로 다시 굽는다.

대표 이미지(1920×1080)를 그대로 쓰지 않은 이유는 비율이다. 카카오톡·슬랙은
카드를 1.91:1 로 자르기 때문에 16:9 를 넣으면 위아래가 잘린다. 세로를 줄이는
대신 가로로 다시 잡았고, 담는 건 딱 한 줄("하.. 답장하기 싫다...")이다.
대화방에서는 카드가 아주 작게 떠서 그 이상은 읽히지 않는다.

카카오톡에서 특히 걸리는 세 가지:

1. **`og:image` 는 절대 URL 이어야 한다.** 상대 경로(`/og.png`)를 주면 카카오
   크롤러가 자기 도메인 기준으로 풀지 못해 이미지를 통째로 버린다. 그래서
   `https://office-firewall.vercel.app/og.png` 로 박아 뒀고, 테스트가
   `^https://` 를 강제한다.
2. **크롤러는 JavaScript 를 실행하지 않는다.** 태그를 런타임에 채우면 카카오는
   빈 카드를 본다. Vite 는 `index.html` 을 그대로 `dist` 로 내보내므로 정적
   HTML 안에 있으면 된다. 테스트가 빈 `content=""` 를 잡는다.
3. **카카오는 URL 별로 OG 결과를 캐시한다.** 이미지를 바꿔 배포해도 한동안
   예전 카드가 그대로 뜬다. 카카오 개발자 도구의 **캐시 초기화**
   (`https://developers.kakao.com/tool/clear/og`, 카카오 계정 로그인 필요)에
   주소를 넣고 한 번 돌려야 새 이미지가 반영된다. 이건 코드로 해결할 수 없어서
   배포 후 수동 작업으로 남는다.

부수 조건도 맞춰 뒀다. 이미지는 리다이렉트 없이 200 으로 바로 응답해야 하고
(`/og.png` 직접 서빙, 실측 확인), `og:image:width/height` 는 실제 파일 크기와
같아야 한다(PNG 헤더에서 읽어 대조하는 테스트가 있다). 나중에 커스텀 도메인을
붙여 apex → www 리다이렉트가 생기면 카카오가 실패할 수 있으니, 그때는
`og:url` 과 `og:image` 를 최종 도메인으로 바꿔야 한다.

### 홈 화면 추가

`public/manifest.webmanifest` + 아이콘 3종(192 / 512 / maskable 512) +
`public/apple-touch-icon.png`(180) 을 넣었다. 아이콘은 상단 로고·파비콘과 같은
도형(방패 + 벽돌)을 그대로 구워서 세 자산의 인상을 한 벌로 맞췄다. 안드로이드는
아이콘을 원형 등으로 잘라내므로 `maskable` 은 사방 여백을 둔 별도 버전이다.

`public/sw.js` 가 있는 이유는 오프라인 지원이 아니다. **안드로이드 크롬은
manifest 만으로는 설치를 제안하지 않고, fetch 핸들러를 가진 서비스 워커가 함께
있어야 `beforeinstallprompt` 를 던진다.** 그 조건을 만족시키는 게 목적이라
캐시는 최소한으로만 쓴다.

서비스 워커가 잘못 캐시하면 배포를 해도 옛 화면이 계속 뜨고, 심사 기간에 그런
일이 생기면 사용자 쪽에서 고칠 방법이 없다. 그래서 두 규칙을 지킨다.

- **HTML 은 항상 네트워크 우선.** 캐시는 오프라인일 때만 쓴다. 배포한 내용이
  캐시에 막히는 일이 없다. (테스트가 `fetch` 가 `caches.match` 보다 먼저
  오는지 확인한다.)
- **`/api/*` 는 절대 캐시하지 않는다.** 캐시된 분석 결과를 다른 입력에
  돌려주면 그건 오답이다.

해시가 붙은 `/assets/*` 만 캐시 우선이다. 내용이 바뀌면 파일 이름이 바뀌므로
낡은 것을 돌려줄 수가 없다. `vercel.json` 에서 `sw.js` 를 `max-age=0,
must-revalidate` 로 내려 서비스 워커 자체가 낡지 않게 했고, `manifest.webmanifest`
의 Content-Type 을 `application/manifest+json` 으로 바로잡았다(로컬 서버는
`application/octet-stream` 으로 내보내고 있었다).

### 설치 배너 — 플랫폼마다 경로가 다르다

- **안드로이드/크롬**: `beforeinstallprompt` 를 잡아 두고, 사용자가 버튼을
  눌렀을 때 `prompt()` 를 부른다. 이벤트 없이 프롬프트를 띄울 방법은 없다.
- **iOS 사파리**: 설치 프롬프트 API 자체가 없다. 공유 시트에서 직접 눌러야 해서
  버튼 대신 그 경로를 문장으로 알려 주고, **누를 수 없는 버튼은 숨긴다.**
- 이미 홈 화면에서 실행 중이면(`display-mode: standalone` 또는 iOS 의
  `navigator.standalone`) 띄우지 않는다.
- 한 번 닫으면 다시 띄우지 않는다. 거절당한 뒤에도 계속 뜨는 설치 배너는 그
  자체가 이 도구에 대한 인상이 된다.

배치와 시점에서 문제를 하나 잡았다. 처음에는 첫 화면에서 바로 띄웠는데,
**첫 방문자는 진입 스토리 모달을 먼저 본다.** 배너가 그 아래에 깔려 보이지도
않았고(실측), 무엇보다 이 도구가 뭘 해주는지 보기도 전에 설치부터 권하는
순서였다. 스토리를 닫은 뒤로 미룬다(`pendingInstall`). 크롬 이벤트는 들고
있으면 나중에 `prompt()` 를 부를 수 있어 미뤄도 잃는 게 없다.

자리는 상단바 바로 아래다. 우하단은 이미 "맨 위로"와 "의견 보내기" 플로팅
버튼이 쓰고 있어서, 거기 두면 실행 버튼까지 세 겹으로 겹친다.

## 설치 배너 · 상담 창구 · 바로가기 자리

### "설치했는데 홈 화면에 없다"

**아이콘이 어디 놓이는지는 OS 와 브라우저가 정한다. 웹에서 위치를 지정할 방법은
없다.** 그래서 고칠 수 있는 건 두 가지뿐이었다: 설치 품질을 올리는 것과, 어디로
갔는지 정확히 말해 주는 것.

manifest 에 `id` 와 `shortcuts` 를 넣었다. `id` 를 비워 두면 크롬이 `start_url`
에서 유추하는데, 나중에 `start_url` 이 바뀌면 "다른 앱"이 돼서 업데이트 대신
중복 설치된다. `shortcuts` 는 아이콘을 길게 눌렀을 때 나오는 바로가기이면서,
안드로이드가 단순 바로가기가 아니라 WebAPK(진짜 앱)로 설치할 근거를 하나 더 준다.

그리고 설치가 끝나면 플랫폼에 맞는 안내를 띄운다. 실제로 간 곳이 다르기 때문이다.

- **안드로이드 크롬**: 홈 화면 + 앱 서랍. 런처 설정에 따라 앱 서랍에만 들어간다.
- **데스크톱 크롬/엣지**: 홈 화면이라는 개념이 없다. 앱 목록·작업 표시줄에 앉는다.
- **iOS 사파리**: 공유 시트로 직접 추가하므로 항상 홈 화면이다.

같은 이유로 배너 제목도 갈아끼운다. 데스크톱에서 "홈 화면에 두고 쓰세요"는 지킬
수 없는 약속이라 "창으로 띄워 두고 쓰세요"로 바꾼다.

### 배너를 띄우는 형태로

문서 흐름에 있던 띠를 `position: fixed` 카드로 바꿨다. 흐름에 두면 배너가 뜨고
질 때마다 아래 내용이 통째로 밀려서 읽던 자리를 잃는다. 실측으로 확인했다.

```
본문 top(배너 있을 때): 52
본문 top(배너 닫은 뒤): 52  → 레이아웃 밀림 없음
배너 top: 62 · 상단바 bottom: 52  → 상단바 아래에 위치
```

`z-index` 는 60 이다. 모달(100)보다 낮게 둬야 진입 스토리나 영수증이 열렸을 때
배너가 그 위로 튀어나오지 않는다.

### EAP 하나로는 부족했다

근로복지공단 EAP 는 **중소기업 재직자·특수고용·프리랜서 등 대상이 정해져 있다.**
해당되지 않는 사람이 누르면 "대상이 아닙니다"로 끝난다. 힘들어서 누른 사람에게
그 경험을 주는 건 이 블록이 하려는 일의 정반대다.

그래서 **조건 없이 누구나 쓸 수 있는 창구를 먼저** 놓고, 조건이 있는 것은 조건을
라벨로 밝혀 뒤에 뒀다.

| 창구 | 대상 | 비고 |
|---|---|---|
| 고용노동부 고객상담센터 **1350** | 누구나 | 직장 내 괴롭힘·근로조건, 무료 |
| 정신건강 상담전화 **1577-0199** | 누구나 | 24시간, 무료 |
| 직장갑질119 | 누구나 | 노무사·변호사가 답변하는 민간 단체 |
| 근로복지공단 EAP | 조건 확인 | 중소기업 재직자·특고·프리랜서 |

전화번호는 `tel:` 로 걸어 뒀다. 힘든 상태에서 번호를 옮겨 적게 하지 않는다.
공유되는 영수증 카드의 안내 문구도 EAP 주소 대신 두 번호로 바꿨다 — 이미지라
링크가 동작하지 않으니 번호가 더 쓸모 있고, 조건도 없다.

순서가 조용히 뒤집히기 쉬운 자리라 `test/care-links.test.js` 로 고정했다.
"조건 없는 창구가 먼저", "누구나 쓸 수 있는 창구가 둘 이상", "EAP 에 조건 라벨"이
깨지면 테스트가 잡는다.

### 바로가기를 본문으로

영수증 모달 맨 아래에 있던 상담·채용 링크를 걷어내고 결과 화면 본문으로 옮겼다.
모달 하단은 작은 화면에서 세로로 긴 영수증 카드에 밀려 잘리거나, 잘리지 않아도
시선이 닿지 않는 자리다. 본문의 "도움받을 수 있는 곳"은 영수증 발급 버튼 바로
위라 이미 지나온 자리이고, 작은 텍스트 링크 대신 손가락이 닿는 크기(실측 60px,

## 설치 배너가 다시 뜨지 않던 이유

"설치했는데 배너가 안 뜬다"는 제보에서 나온 버그다. 원인은 **설치 완료를
'사용자가 닫았다'와 같은 키에 기록한 것**이었다.

```js
window.addEventListener('appinstalled', () => {
  markInstallDismissed();   // ← ofw_install_dismissed_v1 = '1'
  ...
});
```

한 번 설치하고 나면 그 브라우저에서는 `installDismissed()` 가 영원히 참이라
배너가 **다시는 뜨지 않았다.** 앱을 지우고 다시 깔고 싶어도 들어갈 입구가
화면에 없었고, 왜 안 나오는지 알 방법도 없었다.

두 상태를 나눴다. `ofw_install_dismissed_v1`(사용자가 닫음)과
`ofw_installed_v1`(설치됨)은 뜻이 다르다. 그리고 설치 여부는
**`beforeinstallprompt` 가 알려 준다** — 이 이벤트는 "지금 설치할 수 있다"는
뜻이라, 이벤트가 왔다는 건 설치돼 있지 않다는 뜻이다. 그때 설치 키를 지워
상태를 사실에 맞춘다.

여기에 **푸터의 "앱으로 설치"** 를 더했다. 이게 없으면 배너를 한 번 닫는 순간
설치 경로가 화면에서 사라져서, 브라우저 메뉴를 아는 사람만 설치할 수 있게 된다.
푸터에서 열 때는 `force` 로 닫힘 기록을 무시한다.

상태 전이를 실측으로 확인했다(크롬의 설치 신호를 합성 이벤트로 흉내 냈다).

```
설치 가능 신호 → 배너 보임 · 푸터 입구 보임
설치 완료      → 닫힘 키: null · 설치 키: 1   (섞이지 않음)
앱 삭제 후 재방문 → 배너 다시 뜸 · 설치 키 정리됨
사용자가 닫음  → 리로드해도 안 뜸(닫음 존중) · 푸터 입구는 남음
푸터로 다시 열기 → 열림 · 설치 버튼이 prompt() 호출
```

`test/share-and-pwa.test.js` 에 소스 가드를 넣었다. `appinstalled` 핸들러가
닫힘 키를 건드리면, `beforeinstallprompt` 가 설치 키를 정리하지 않으면, 푸터
입구가 사라지면 테스트가 잡는다. 증상이 조용한 버그라 다시 이 자리로 돌아오기
쉽다.

### 영수증의 채용 링크

지난번에 영수증 모달의 링크를 전부 걷어냈는데, 카드 안의 **"[원티드 커리어
세이프]"** 문구는 이미지라 누를 수가 없어서 제안만 있고 갈 곳이 없는 상태가
됐다. 채용 링크만 되돌렸다.

상담 창구는 되돌리지 않았다. 둘은 성격이 다르다. 상담 창구는 대상·조건 설명이
함께 있어야 뜻이 통하고(없으면 해당 없는 사람이 헛걸음한다) 그만한 공간이
모달에 없다. 채용 링크는 한 줄로 끝난다.

자리는 **저장·복사 버튼 바로 아래**다. 예전처럼 모달 맨 끝에 두면 세로로 긴
영수증 카드에 밀려 작은 화면에서 스크롤을 끝까지 내려야 보인다. 실측으로
iPhone 13 에서 높이 45px, 뷰포트 안에 들어오는 것을 확인했고, 클릭하면 새 창이
열린다(`target="_blank"` + `rel="noopener noreferrer"`).

직장갑질119 주소는 `https://gabjil119.campaignus.me/` 로 바로잡았다.

## 푸터 겹침 · 앱 이름 · 브라우저별 설치 · 모바일 줄바꿈

### 푸터 버튼이 떠 있는 버튼에 가려지던 문제

"의견 보내기"와 "앱으로 설치"가 다른 문구들과 같은 줄에 섞여 흘렀다. 모바일에서는
그 줄의 오른쪽 끝에 걸리는데, 하필 거기가 떠 있는 '맨 위로' 버튼 자리였다.

두 겹으로 고쳤다. 폭 100%짜리 빈 칸(`.footer-break`)으로 **줄을 강제로 끊어**
버튼들이 항상 새 줄에서 시작하게 했고, `wouldCover` 의 가림 판정 대상에 푸터
버튼 두 개를 추가해 그래도 겹치면 떠 있는 버튼이 숨도록 했다.

덤으로 하나 더 잡혔다. 줄을 끊고 나니 첫 줄 끝에 구분점(·)이 홀로 남아 오타처럼
보였다. 좁은 화면에서는 두 문구를 각자 줄에 놓고 점을 숨긴다.

### 홈 화면 라벨

`short_name` 이 "방화벽"이었다. 그것만 보면 보안 앱으로 읽힌다. 안드로이드·iOS
모두 라벨을 10~12자 안팎에서 자르기 때문에 "OFFICE FIREWALL"(15자)은
"OFFICE FIRE…" 가 된다. **"직장 메시지 방화벽"(10자)** 로 바꿨다 — 자르지 않고
들어가면서 무슨 앱인지도 드러난다. `apple-mobile-web-app-title` 도 같은 값으로
맞췄고, 두 값이 어긋나면 테스트가 잡는다.

### 브라우저별 설치 경로

`beforeinstallprompt` 는 **크로미움 일부에만 있는 비표준 이벤트**다. 그 이벤트가
오지 않는 브라우저에서 "설치" 버튼을 띄워 두면 눌러도 아무 일도 일어나지 않는
버튼이 되고, 사용자는 그걸 고장으로 읽는다. 삼성 인터넷에서 "보안상 문제로 설치가
안 된다"고 느껴진 것도 이 모양이었을 가능성이 크다.

그래서 **프롬프트를 실제로 띄울 수 있을 때만 버튼을 남기고**, 그렇지 않으면 그
브라우저의 실제 경로를 문장으로 알려 준다.

| 환경 | 설치 버튼 | 안내 |
|---|---|---|
| 크롬·엣지·웨일 | 이벤트 오면 표시 | 메뉴(⋮) → "앱 설치" |
| 삼성 인터넷 | 이벤트 없으면 숨김 | 메뉴 → "현재 페이지 추가" → "홈 화면" |
| iOS 사파리 | 숨김(API 없음) | 공유 → "홈 화면에 추가" |
| iOS 크롬·파폭 | 숨김 | 사파리로 열어야 한다고 안내 |
| 파이어폭스(안드) | 숨김 | 메뉴(⋮) → "홈 화면에 추가" |
| **카카오톡·네이버 인앱** | 숨김 | **설치 불가 — "다른 브라우저로 열기"** |

인앱 브라우저가 한국에서는 특히 중요하다. 카카오톡으로 공유한 링크는 대부분 카카오
인앱에서 열리는데 거기서는 설치가 아예 불가능하다. 그 상황에서 필요한 건 설치
방법이 아니라 "기본 브라우저로 열어라"이고, 배너 제목도 "설치하세요"가 아니라
"브라우저에서 열면 앱으로 설치할 수 있어요"로 바뀐다.

판정 순서에 함정이 하나 있다. **인앱 브라우저의 UA 에는 Chrome/Safari 표기가 함께
들어 있어서**, 크로미움 판정을 먼저 두면 인앱은 영영 걸리지 않는다. 테스트가 이
순서를 고정한다.

### 모바일 줄바꿈 전수조사

이전 조사는 PC 폭 기준이었다. 360/390/414px 에서 요소별 줄 상자를 실측해 다시 훑었다.

원인은 하나였다. 본문 여러 곳이 문자열 안의 `\n`(`pre-line`)과 `<br>` 로 줄을
강제하는데, **그 위치가 전부 데스크톱 폭에서 문장당 한 줄이 되도록 고른 값**이었다.
좁은 화면에서는 같은 문장이 이미 2~3줄로 접히니, 강제 개행이 그 위에 반쪽짜리 줄을
하나 더 만든다. 실측하면 최대 폭의 **19%밖에 안 되는 중간 줄**이 생겼다.

모바일에서만 분기했다.

- `pre-line` 을 쓰는 네 곳(`.choice-note`·`.care-body`·`.replies-mode-note`·
  `.restored-note-body`)은 480px 이하에서 `white-space: normal` 로 흘린다.
  문장은 마침표로 이미 끝나 있어 뜻이 흐려지지 않는다.
- HTML 의 `<br>` 25개를 전수 분류해 **산문 구분자 16개**에만 `.br-wide` 를 달아
  480px 이하에서 숨긴다. 헤드라인·인용문·라벨 구분자·영수증 카드(고정 폭 이미지)
  안의 9개는 짧은 줄이 의도라서 그대로 뒀다.
- `.busy-note-body` 도 예외다. 세 줄이 "지금 무슨 일인지 / 무엇이 빠졌는지 /
  언제 다시 오면 되는지"로 성격이 달라서, 한 문단으로 흘리면 재시도 시각이
  문장 속에 묻힌다.

여기서 함정을 하나 밟았다. **`<br>` 을 `display: none` 으로 숨기면 앞뒤 문장이
공백 없이 붙는다**("보입니다.눌러서"). 숨기는 자리마다 공백을 함께 넣어
(`…보입니다. <br class="br-wide" />눌러서…`) 데스크톱 렌더링은 그대로 두고 모바일에서만
한 칸이 남게 했다.

마지막으로 고아 줄(문단 끝에 한두 단어만 남는 경우)에는 `text-wrap: pretty` 를,
제목에는 `text-wrap: balance` 를 줬다. 지원하지 않는 브라우저는 무시할 뿐이라
회귀가 없다.

강제 개행이 만들던 짧은 중간 줄은 세 폭 모두에서 사라졌다.

테스트 190 → **194개**, 전부 통과.


## 영수증에서 "심리적 체감 지표"를 걷어냈다

카드에 이런 줄이 있었다.

```
심리적 체감 지표
막아낸 야근(환산)      +5.5 Hours
지킨 멘탈(환산)        +85 HP
사내 정치 리스크        5% (평판 유지)
* 심리적 체감 지표는 실측값이 아니라, 방어 행동 후 체감을 참고로 환산한 값입니다
```

세 가지가 걸린다.

1. **근거가 화면 어디에도 없다.** 이 서비스가 내세우는 건 "계산 과정을 그대로
   펼쳐 보여준다"이고, 위험 지수에는 판정 근거 표와 계산식이 함께 붙는다.
   저 세 숫자만 그 규칙 밖에 있었다.
2. **답장과 아무 관계가 없다.** `hoursSaved` 는 긴급도와 점수로, `mentalHp` 는
   점수로, `politicalRisk` 는 말투로만 계산된다. 실제로 답장을 보냈는지, 셋 중
   무엇을 골랐는지는 들어가지 않는다. **아무것도 하지 않아도 "막아낸 야근
   +5.5h"가 똑같이 찍힌다.**
3. 면책 문구를 달아야 했다는 것 자체가 신호였다. "실측값이 아니다"라고 적으면서
   숫자는 소수점까지 보여주는 카드는, 공유되는 이미지라 더 그렇다.

`hoursSaved`·`mentalHpSaved`·`politicalRisk` 와 그 테스트까지 함께 지웠다.
화면에서 안 쓰는 계산은 남겨 두면 나중에 "왜 있지?"가 된다. 대신
**근거 없는 환산 지표가 다시 들어오지 않는지** 확인하는 테스트를 하나 세웠다
(`buildReceiptData` 의 키 목록을 통째로 고정한다).

카드에 남는 건 전부 화면 어딘가에 근거가 있는 값이다 — 위험 지수(판정 근거 표),
빌런 유형(규칙), 직군·연차(내가 고른 값), 방어 모드(내가 고른 값), 발급 횟수(실제 횟수).

곁가지로 카드가 짧아졌다. 내보내는 PNG 가 **760×1474 → 760×1136** 로 23% 줄어,
대화방 미리보기에서 덜 잘린다.
